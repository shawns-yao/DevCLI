# 包边界收敛（一）：提取运行时事件模型与渲染侧 HITL 处理器

## 背景

`PackageBoundaryTest` 扫描 `import com.devcli.X.` 发现若干顶层包之间的循环依赖。2026-09-19 先断开了 `llm → runtime`（见 `0003`），本次处理剩余五条中的两条——它们根因清晰、改动有界：

### 环一：`agent ↔ runtime`

```
agent → runtime : 仅 runtime.event（RunEvent / RunEventSink / RunEventStreamListener），5 个文件
runtime → agent : Agent / AgentTurnInbox，6 个文件
```

**`agent` 需要 `runtime` 的原因只是事件模型**。事件模型是「运行过程中发生了什么」的数据结构，本身不依赖会话编排；它被放在 `runtime` 里，只因为最初是随运行时而生的。于是 `agent` 为了拿到事件类型，被迫依赖了整个 `runtime`——而 `runtime` 反过来又依赖 `agent`。

### 环二：`hitl ↔ render`

```
hitl → render : 仅 RendererHitlHandler 依赖 Renderer，1 个文件
render → hitl : Renderer / PlainRenderer / InlineRenderer / InlineApprovalPrompter
                依赖 ApprovalRequest / ApprovalResult / ApprovalPolicy，4 个文件
```

**`hitl` 里混了两类东西**：审批闸门与策略（`ApprovalGate` / `ApprovalPolicy` / `HitlHandler`）和「用渲染器实现的处理器」（`RendererHitlHandler`）。后者是适配器，它必须认识渲染器，于是把 `hitl` 拖向 `render`。

## 决定

**环一：把 `runtime/event/` 提取为顶层包 `com.devcli.event`。**

三个类随之下沉。该包**不是叶子包**——`RunEvent` 引用 `llm` 的消息类型与 `tool` 的输出类型，提取后会新增 `event → llm`、`event → tool` 两条边。这两条都不构成新环（`tool` 不依赖 `event`），方向也合理：事件模型描述的是「模型产出了什么、工具返回了什么」，指向这两层是自然的。

**环二：把 `RendererHitlHandler` 从 `hitl` 移到 `render`。**

`render → hitl` 已是既定方向（渲染器要展示审批请求），把适配器放进 `render` 保持这个方向不变，同时消除反向依赖。它唯一的调用方是 `cli/Main`，改动面为一行 import。

## 关键取舍

**为什么提取事件模型，而不是让 `agent` 自带一份事件类型。** 事件类型是 `runtime`、`agent`、`render`、`hook`、`trace`、`session` 共用的契约；复制一份会产生两套不兼容的事件定义，比循环依赖更糟。

**为什么 `RendererHitlHandler` 放 `render` 而不是 `cli`。** `cli` 是入口层，`PackageBoundaryTest` 断言「任何包都不得依赖 `cli`」。把它放进入口层会把一个被适配的类型绑死在入口，其它渲染形态（如未来的 TUI 之外的形态）无法复用。放 `render` 则与 `Renderer#promptApproval` 同处一地。

**为什么不同时处理三条 `tool` 相关的环。** `tool ↔ mcp`、`tool ↔ rag`、`tool ↔ workspace` 的 `X → tool` 方向虽然也薄（`rag` 仅需 `ToolSideChannel`，`workspace` 仅需 `ToolRegistry`），但修法涉及把 tool 的 SPI 类型下沉，影响面远大于本次两条。分开处理可以让每次变更都可独立验证、独立回退。

## 后果

- `agent → runtime` 断开；`runtime → agent` 保留（单向，不再成环）。`PackageBoundaryTest` 可新增 `agent` 不得依赖 `runtime` 的断言。
- `hitl → render` 断开；`render → hitl` 保留。可新增 `hitl` 不得依赖 `render` 的断言。
- 新增顶层包 `com.devcli.event`，**不属于叶子包**（依赖 `llm` 与 `tool`）。
- 剩余三条环（`tool ↔ mcp`、`tool ↔ rag`、`tool ↔ workspace`）仍在 `TODO.md` 中，待后续单独处理。
