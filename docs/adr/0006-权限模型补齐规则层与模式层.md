# 权限模型对齐分层求值链：补齐规则层、模式层与分类器，取代单层授权

> **本文的三类规则、短路顺序与分类器输入已由 [ADR 0013](0013-自动审批网关规则与可信意图上下文.md) 取代。**

> **本文「分类器」一节的超时默认值已于 2026-09-23 就地修订。**
>
> 原判断是「不预设一个『正确』默认值，而是把权衡写进文档」，理由是「两边都要权衡」。该理由把两类代价当成了对称的，实际不对称：设得过短导致 fail-closed 误拒，`auto` 退化为「大面积拒绝」且用户无从诊断；设得过长只是延迟，超时本身仍是 fail-closed，**不损失安全**。因此改为预设一个按实测中位延迟校准的保守默认值（10 秒 → 30 秒），并把「可按端点调整」直接写进超时拒绝消息，而不是只写进文档。
>
> 超时修订只影响默认值与提示方式；当前求值链与规则语义以 ADR 0013 为准。

## 背景

DevCLI 当前的授权审批只有一层：`ApprovalGate` 的三值判定（`ALLOW` / `HITL` / `DENY`），外加硬编码的策略边界（`PathGuard` / `CommandGuard` / `SensitivePathPolicy`）。

把它放到分阶段求值链里对照，`ApprovalGate` 只对应**权限模式基线策略**这一步，而它前面的 **deny 规则**、**allow 规则**、**ask 规则**三步完全不存在。由此产生三个已确认的问题：

1. **授权只能放宽，不能收紧。** 系统没有用户可用的 deny 通道。ADR 0005 引入的 `TaskGrant.merge` 采用并集语义，一旦基线授权 `src/**`，用户无法为高风险任务临时收紧到 `src/a.java`。安全机制里「只能放宽不能收紧」是方向性错误。
2. **「一轮任务」是模型缺失后的补丁。** `TaskGrant` 一轮失效、`approvedAll` 每轮任务开始清空，都源于缺少「会话节奏」这一层。当规则可以持久、模式可以常驻时，「一轮」这个边界不需要存在。
3. **匹配粒度是资源维度，不是用户意图。** `writeGlobs` / `networkHosts` / `projectCommands` 回答的是「能碰哪些资源」；用户想表达的是「我在做这个重构，别打断我」。维度不对齐，才会出现「同类任务反复授权」的疲劳。

把 hooks 一并放进来对照，缺口更清楚：`HookDispatcher.Decision` 只有 `CONTINUE` / `WARN` / `BLOCK`——hooks 能收紧、不能放宽；`ApprovalGate` 能放宽、不能收紧。两套机制各自只有一半，合起来才勉强是一条求值链，而且顺序是隐式的。

ADR 0005 试图在这套单层模型上增加「持久基线」。它只是把基线策略喂得更好，没有补上缺失的规则层——这是本次决定取代它的原因。

硬约束：

- `deny` 必须永远优先于任何模式与任何授权，不存在覆盖它的通道
- 确定性层（规则层与模式层）的判定权威不引入模型；分类器只能接管求值链末端仍为 `ask` 的动作
- 分类器不可用、超时或连续失败时必须 fail-closed
- 已有的工程资产不得丢失：参数级资源槽判定、沙箱集成、隔离工作区与 PatchSet、委派能力范围收窄、审计身份
- 项目级配置必须能防「第三方仓库提交 settings 放宽本地边界」

## 决定

采用三层结构：**规则层 → 模式层 → 分类器**，并复刻完整的分阶段求值链。

### 求值链

策略硬边界（路径越界、命令黑名单、非法 URL scheme）排在规则层之前，不属于第 7 阶段。WorkBuddy 的第 3 阶段是「高危命令强制 `ask`」，而 DevCLI 的 `CommandGuard` 是硬拒绝——若按字面顺序把可信 `allow` 放在它之前，一条宽泛的放行规则就能绕过命令黑名单。因此这里显式前移：硬边界先判定并直接 `DENY`，规则层只在它通过后生效。

其余阶段按固定顺序判定，任一步命中即终止：

| 阶段 | 检查项 | 命中后行为 |
| --- | --- | --- |
| 0 | Hooks | 现有 `CONTINUE` / `WARN` / `BLOCK`；`BLOCK` 立即拒绝 |
| 1 | deny 规则 | 立即拒绝，最高优先级 |
| 2 | allow 规则 | 命中即放行；先于 ask 短路，见下 |
| 3 | 命令安全检查 | DevCLI 前移为硬边界：高危命令直接 `DENY`，见上文 |
| 4 | ask 规则 | 命中即强制 ask；被更宽的 allow 覆盖时不会生效，加载期告警 |
| 5 | bypass 短路 | `bypassPermissions` 放行大多数动作 |
| 6 | 不可信 allow 规则 | 可放行，但不能越过第 3 阶段 |
| 7 | 模式基线策略 | 现有 `ApprovalGate` 逻辑 |
| 8 | 非交互兜底 | 无法弹审批框时把 `ask` 转为 `deny` |
| 9 | `dontAsk` 收口 | 把 `ask` 改写为 `deny` |
| 10 | `auto` 分类器 | 只接管到此仍为 `ask` 的动作；不可用或连续失败按 `deny` |

第 0 阶段保持**只收紧**：hooks 不获得放宽能力。放宽一律走规则层，避免两处都能放宽导致「哪个先命中」无法推理。

规则层严格照 WorkBuddy 的次序：第 2 阶段 `allow` 命中即短路放行，第 4 阶段 `ask` 才轮到，两者之间**不做**「谁更具体」的比较。这里曾实现过一版按 specifier 字面量长度计算的「具体度」比较，核实 WorkBuddy 官方文档后回滚——其求值链没有这个机制，且该度量本身会判反：`**/secret/**` 的字面量前缀是空串，语义上却比 `src/**` 更窄。把会在边缘案例判反的启发式放进安全判定，比写死一个顺序危险得多。

固定次序的代价是真实的：`allow write_file(src/**)` 配 `ask write_file(src/secret/**)` 时，后者永远不会生效，用户却以为自己声明了例外。这个坑由加载期的 `PermissionRuleSet.shadowedAskRules()` 提示，告警里直接给出正确做法（例外改用 `deny` 声明）。启发式只配做告警：误报的代价是用户多看一眼，误判的代价是安全漏洞。

真正的解法是第 4 阶段的信任分层——让 `ask` 夹在「可信 allow」与「不可信 allow」之间，按规则**来源**而非 glob 形状取胜。DevCLI 目前只有一个规则来源，信任分层落地前，次序问题靠显式告警兜住，不靠改次序。

### 规则语法

规则形态为 `Tool` 或 `Tool(specifier)`。工具名可写 DevCLI 原生名，也可写 WorkBuddy 风格别名（`Edit` → `edit_file`、`Write` → `write_file`、`Read` → `read_file`、`Bash` → `execute_command`、`WebFetch` → `web_fetch`、`WebSearch` → `web_search`），别名在解析时归一，只保留一套匹配语义。

specifier 只对已声明资源槽的工具有效（`ToolResourceSlot`）：路径类 `write_file` / `edit_file` / `delete_files` / `create_project` 写项目相对 glob，命令类 `execute_command` 写命令模式，网络类 `web_fetch` 写裸域名或 `domain:` 前缀。给没有资源槽的工具（`revert_turn` / `apply_patch` / 全部 MCP 工具）写 specifier 会在解析时被拒绝，不留一条永远不匹配的规则。工具名支持末尾通配（`mcp__*`）与全局通配（`*`）。

命令类 specifier 三种形态：`X:*` 与 `X *` 按词边界前缀匹配（`git:*` 匹配 `git` 与 `git status`，不匹配 `gitleaks`）；不含 `*` 时精确匹配；其余按 `*` / `?` 通配匹配整个子命令。

复合命令解析 `&&` / `||` / `;` / `|`，对每个子命令独立判定：deny 与 ask 规则任一子命令命中即触发；**allow 规则要求全部子命令命中**。含重定向（`>` / `<`）的命令在 allow 规则下通配形态一律失效，只接受精确匹配。拆分不做引号感知，可能把带引号的片段切错——两个方向都只会更严格，不会放宽。

`delegate_task` 与 `load_skill` 目前没有资源槽，只支持裸工具名；`Agent(Explore)` 这类角色级 specifier 需要先定义角色资源槽，本次不做。

### 模式

`default` / `plan` / `acceptEdits` / `dontAsk` / `bypassPermissions` / `auto`。

#### 两根轴，不是一根

WorkBuddy 把权限分成互补的两层：**模式层**约束「想不想用」某工具或访问某路径，**沙箱层**约束 Bash 子进程在 OS 层「能不能真的访问」某资源。模式不是权限系统的全部逻辑。

DevCLI 现有的 `ToolAccessScope` 同时干了两件事，必须先按职责拆开：

| 维度 | 归属 | 现有机制 |
| --- | --- | --- |
| 默认放行还是默认询问 | 模式层 | `hitlHandler.isEnabled()` 升级为询问策略 |
| 能力上限（写工具是否暴露给模型） | 模式层 | `ToolAccessScope.READ_ONLY`，由 `plan` 模式驱动 |
| 命令在主机还是隔离后端执行 | 沙箱层 | `ToolAccessScope.ISOLATED_PROJECT`，由委派、计划任务与步骤执行器在内部施加 |

`ISOLATED_PROJECT` 已经核查过：它没有任何用户可见的开关，调用点全在 `DelegationSession`、`PlanTaskWorkspaceExecutor`、`StepExecutionCoordinator`——按执行上下文施加，不由用户切换。所以它天然不进模式，也不需要新增开关。

`ToolAccessScope.narrow()` 已经能取交集，所以模式层的 `READ_ONLY` 与沙箱层的 `ISOLATED_PROJECT` 同时生效时自动收敛为 `READ_ONLY`，不需要新的组合逻辑。

**因此不新增第三套开关**：模式层是唯一用户可见的预设。`/readonly` 与 `/hitl` 已被 `/mode` 取代并删除——两个旧命令各只覆盖一根轴（前者是能力上限，后者是询问策略），而模式同时声明两者，留着它们只会造出「命令与模式哪个说了算」的二义性。切换模式时清空 `approvedAll`，避免旧的「全部放行」被当成当前授权。

#### 模式取值

| 模式 | 能力上限 | 询问策略 | 生效阶段 |
| --- | --- | --- | --- |
| `default` | FULL | 询问 | 常规路径 |
| `plan` | READ_ONLY | 询问 | 能力上限在任务入口施加 |
| `acceptEdits` | FULL | 编辑类工具放行 | 规则层之后、任务授权之前 |
| `bypassPermissions` | FULL | 直接放行 | 规则层之后、任务授权之前 |
| `dontAsk` | FULL | 收口为拒绝 | 所有放行路径之后 |
| `auto` | FULL | 分类器 | 第 10 阶段 |

「编辑类工具」判定复用 `ToolResourceSlot`：资源槽为 `PATH` 的工具（`write_file` / `edit_file`）。删除类（`PATH_LIST`）与项目创建类（`PROJECT_NAME`）不算编辑——用户说「接受编辑」时没有同意删文件。

#### 为什么三个模式的生效阶段不同

这不是实现顺序问题，是语义要求：

- `bypassPermissions` 要**早**——它在任务授权之前放行；放晚了，「不询问」会被任务授权范围二次约束，等于没生效。
- `dontAsk` 要**晚**——它只把「本来会询问」的动作收口为拒绝，不能覆盖显式授权与规则层 `allow`。放早了会把 `TaskGrant` 的显式放行一起吃掉。
- `acceptEdits` 居中——编辑类工具直接放行，其余落到常规路径。

这与 WorkBuddy 的求值链一致：`bypassPermissions` 在第 5 阶段短路，`dontAsk` 在第 9 阶段收口。

#### 模式不能越过的东西

- **策略硬边界**（项目根围栏 / 命令黑名单）永远在模式之前，`bypassPermissions` 不例外。这是本文已确认的刻意偏离：WorkBuddy 第 3 阶段是「高危命令强制 ask」，DevCLI 的 `CommandGuard` 是硬拒绝。
- 规则层 `deny` 不被任何模式改写。
- 规则层显式 `ask` 不被 `acceptEdits` / `bypassPermissions` / `auto` 改写——用户已经表达了「这个要问我」。
- `dontAsk` 不把 `allow` 改写为 `deny`，只收口未决的询问。

#### 状态显示

状态栏的 `HITL: ON/OFF` 单布尔位替换为模式位。沙箱不占位——它由内部执行上下文施加、用户不可见，把它显示出来只会让「我在沙箱里」和「我不被询问」两件事看起来是同一件事。

### 分类器（`auto`）

`auto` 是模式，分类器是它的收口实现：求值链走到第 10 阶段仍为 `ask` 的动作才交给分类器，分类器返回 `allow` 或 `deny`，不返回「继续询问」。

必须同时满足：

- 显式 `ask` 规则命中的动作不进分类器——用户已经表达了「这个要问我」
- 调用失败、超时、返回不可解析一律按 `deny`，不做猜测
- 连续失败达到阈值后自动退出该模式并回落到 `default`，不静默降级为放行
- 分类器接收当前动作与**渲染并中和过的对话历史**（工具名、参数、项目路径、当前模式、历史）。历史是意图判定的唯一来源，输入中和是配套前提；判定取向为默认放行。本文原写「只接收最小上下文，不继承会话历史与记忆」，已由 `docs/adr/0012` 推翻

#### 接管范围：只有「没有别的理由要问」的动作

`auto` 不是「所有动作都问分类器」。删除阈值、命令删除确认、`apply_patch` 删除或移动、`revert_turn`、浏览器与 MCP 的逐次审批、显式 `ask` 规则——这些都有独立于默认策略的询问理由，分类器一律不介入。只有走完整条求值链、没有任何规则或安全机制要求询问、仅仅因为默认策略是「问」的动作，才交分类器。

实现上体现为两个出口：`askOrDeny` 是「必须问」，`askOrClassify` 是「默认要问」，只有后者在 `auto` 模式下回调分类器。合并成一个出口会让分类器悄悄接管删除确认这类硬要求。

#### 不覆盖规则层 `allow`

分类器只在规则层**未决**时被调用。用户写了 `allow` 就是用户自己的选择，`auto` 不把它改写掉。代价要写清楚：一条无 specifier 的宽泛 `allow` 会让分类器在该工具上完全不参与——`auto` 形同虚设，而用户以为自己开了自动判断。

这里**刻意不做**「会话内对过宽的 allow 规则做临时过滤」（本文档前一版曾如此规定）。那会在用户看不见的地方改写他显式声明的规则集，正是本项目反复识别的缺陷模式「隐形的第二套机制」；而且「过宽」没有可判定的定义，只能靠 glob 形状猜——启发式只配做告警，不配做判定。

改为在加载期告警：`auto` 模式下存在无 specifier 的 `allow` 规则时，提示「这些规则会让分类器在这些工具上不被调用，想要自动判断请去掉它们」。判定条件是确定的（无 specifier 的 `allow` 覆盖该工具的全部调用），不是形状猜测，因此可以进告警。

#### 调用与失败

- **同步调用**，超时默认 30 秒（`devcli.permission.classifier.timeout.seconds`，取值 1～120）。决策必须在动作执行前做出，没有异步的余地。
- **默认值按实测端点延迟校准（2026-09-23 修订，原为 10 秒）**：10 秒是按快端点定的。实测同一批样本在 10 秒超时下 **14/21 超时**，逐样本延迟中位 **12.0 秒**、**13/21 超过 10 秒**，全部 fail-closed 成拒绝；放宽到 30 秒后 21/21 可评分。30 秒约为实测中位延迟的 2.5 倍。
- **代价不对称，这是推翻「不预设默认值」的理由**：设得过短是 fail-closed 误拒，`auto` 退化成「大面积拒绝」的模式，而用户看到的只有 `[分类器] 已拒绝：权限分类器超时`——无从判断是端点慢还是动作危险，也没有任何提示指向可调参数；设得过长只是让每个未决动作最多等那么久才被拒绝，超时本身仍是 fail-closed，**不损失安全**。把「功能失效」与「延迟」当作对称代价，是原判断的错误之处。
- **超时拒绝消息必须自解释**：消息里直接给出超时秒数与可调参数名，用户不必先读文档才知道能调。**30 秒仍是按已实测的端点定的**，更慢的端点依然需要上调——这一条不因默认值改变而失效。
- 超时、异常、响应不可解析一律 `deny`，不重试、不猜测。
- 连续失败计数由主 Registry 与项目 fork 共享；默认 3 次（`devcli.permission.classifier.failure.threshold`）后自动退出 `auto`、回落 `default` 并提示用户。手动切换模式会重置计数，不把旧模式的故障带入新一轮 `auto`。
- 工具剩余时间不足以覆盖分类器超时时直接 `deny`，不让分类器吃掉工具预算。
- 放行与拒绝都写审计，审批来源标记为 `permission_classifier`，与人工审批、规则层、模式层区分开。
- 分类器未装配时直接 `deny` 并计入连续失败，不回退人工询问。
- 提示词落在 `src/main/resources/prompts/permission-classifier.md`，与代码分离；允许可信的用户级 `~/.devcli/prompts/` 覆盖，但忽略项目级同名 Prompt，避免仓库内容改写自身审批策略。

### 存储分层

作用域优先级：`flag/cli/session > user > policy > project > project-local`。

`deny` 数组从所有作用域合并，任一作用域 deny 即拒绝。

### 可信与不可信 allow 分层

项目目录未被显式信任时，仓库内 settings 的 `allow` 规则归入第 6 阶段，不能越过命令安全检查。用户在交互界面确认信任后，项目级规则提升到第 2 阶段。

### `TaskGrant` 重新定位

`/grant` 从「给下一轮任务授权」改为「写会话级规则」。

`TaskGrant` 承载的运行时作用域（绑定项目、可撤销、fork 共享、`grantId` 审计）保留，其内容改为「当前生效规则集的运行时投影」。生命周期从「一轮」改为「会话」，直到用户切换模式或显式撤销。

### 实施阶段

1. **规则层**（已落地 2026-09-21）：`ToolResourceSlot` / `PermissionRule` / `PermissionRuleSet` / `PermissionEvaluator`，用户级 `permissions.deny` / `ask` / `allow` 与审批链接线
2. **模式层**（已落地 2026-09-21，见上文「模式」段）：`PermissionMode` + `/mode` 切换 + 状态栏模式位 + 询问策略在 `HitlToolRegistry` 的生效点；`/readonly` 与 `/hitl` 删除。实施中发现并修掉一个致命缺陷：`applyHitl` 开头的 `hitlHandler.isEnabled()` 早退排在规则层之前，而 HITL 默认关闭——用户写的 `deny` 规则默认完全不生效
3. **分类器层**（已落地并于 2026-09-21 补强，见上文「分类器（`auto`）」段）：`auto` 模式 + 分类器调用 + fail-closed 与退出策略。分类器落 `hitl`——`policy` 不得依赖 `llm`，且是纯确定性层；提示词独立成资源文件。补强覆盖硬审批旁路、项目 Prompt 隔离、跨 fork 失败计数、模式切换复位和工具预算预检。ADR 前一版规定的「会话内对过宽的 allow 规则做临时过滤」在本阶段删除，理由见该段
4. **存储层**：settings 分层 + 可信 / 不可信分层
5. **交互层**：权限面板（查看规则、来源作用域、临时增删）

第 1 阶段只接入用户级规则。规则集为空时审批链行为与引入规则层之前一致：`HitlToolRegistry.permissionRules` 默认为空，`PermissionEvaluator` 直接返回未决，删除阈值与授权分支走原路径。作用域分区与 `RuleScope` 留到第 4 阶段——在项目级来源出现之前引入作用域枚举，只会造出没有来源的取值。

## 关键取舍

**为什么不在现有单层模型上继续加。** ADR 0005 已经试过一次：加持久基线。结果是「只能放宽不能收紧」，因为真正缺的是 deny 通道而不是基线。在错误的层上叠加，只会让边界更难推理——用户需要同时理解资源维度授权、持久基线、放行缓存三者如何交互。

**为什么本次就做分类器，而不是只交付确定性层。** 只做规则层与模式层能补上「不能收紧」和「一轮边界」两个问题，但补不上「同类任务反复授权」——规则由用户手写，写不全就还得点。分类器直接降低打断频率，这是本次的首要目标。代价必须写清楚：判定权威引入模型、每次走到末端的 `ask` 多一次模型调用、结果不可确定性复现（测试必须注入桩）。约束随之收紧：只接管末端仍为 `ask` 的动作，显式 `ask` 规则不进分类器，失败即 `deny`，连续失败自动退出。

还有一条代价无法靠约束消除：**分类器误判放行时没有人工兜底**。fail-closed 只兜住「分类器不可用」，兜不住「分类器判断错误」——一次错误的 `allow` 就是一次无人复核的放行。`dontAsk` 与 `bypassPermissions` 分别站在「宁拒不误放」与「全放」两端，`auto` 落在中间：它用模型判断换掉人工确认，这既是它存在的理由，也是它的固有风险。要消除这一点，只能在分类器返回 `allow` 时仍然弹确认——那 `auto` 就不再降低打断频率，也就没有存在意义。

反过来，如果首要目标是「边界完全可推理、且不接受任何额外模型调用」，那么只交付确定性层、把分类器留到以后是更好的选择——这也是本次被放弃的那个方案。

**为什么统一到规则语法，而不并存资源维度授权。** 两套并存意味着两套匹配语义、两套文档、两套测试，以及用户无法判断某次放行由哪套决定。`Edit(src/**)` 能表达 `writeGlobs` 的全部语义，表达力还更强（可按文件名模式、可精确到单个文件）。迁移成本是一次性的，并存成本是长期的。

**为什么保留 `TaskGrant` 而不直接删除。** 它承载的不只是资源清单，还有运行时作用域绑定、可撤销性、fork 共享标记和审计身份。这些在纯规则模型里没有对应物，属于已经建成的工程资产。改的是它的内容来源与生命周期，不是它本身。

**为什么必须做可信与不可信 allow 分层。** 引入项目级 settings 后，第三方仓库可以提交 `.devcli/settings.json` 把宽泛的 allow 规则塞进来。缺少这个分层，克隆一个陌生仓库就等于放宽本地安全边界。

这里不能拿 hooks 当先例安慰自己。`HookConfigLoader` 确实已经在读 `<project>/.devcli/hooks.json` 且不做信任检查，但 `HookDispatcher.Decision` 只有 `CONTINUE` / `WARN` / `BLOCK`——项目级 hooks 只能**收紧**，不能放宽，所以那个洞不构成权限提升。`allow` 规则一旦进入项目级作用域，风险方向就反过来了，必须靠信任分层拦住。`SensitivePathPolicy` 保护 `.devcli/config.json` 防的是 Agent，这里要防的是仓库作者。

**为什么不保留双跑过渡期。** `/grant` 与规则表若同时生效，用户无法判断哪条规则在起作用，排障成本远高于一次性切换。迁移按「先建规则层 → 再切 `/grant` → 最后移除旧基线字段」的顺序做，中间不留双读窗口。

## 后果

- `ApprovalGate` 从「三值判定器」降为求值链中「模式基线策略」这一步的实现。它的参数级资源槽逻辑保留，但改为由规则匹配驱动，不再硬编码 6 个工具名的分支。
- ADR 0005 引入的 `permissions.baseline` 被 `permissions.defaultMode` 加 `permissions.allow` / `ask` / `deny` 取代，**已于 2026-09-21 移除**：`PermissionsConfig.baseline` 字段、`BaselineGrant` 类型、`Main.loadBaselineGrant` 与 `baselineGrantSummary` 静态字段，以及三条断言基线行为的测试一并删除。`TaskGrant.merge` 的并集语义随之废弃，`merge` / `mergeGlobs` / `union` 三个方法已删除；`TaskGrant` 本身按上文「`TaskGrant` 重新定位」保留。持久授权改由规则层 `permissions.allow` 承载——它与 `permissions.baseline` 语义完全重叠，这正是旧字段可以整体删除而不损失任何表达能力的原因。
- 新增公共类型：`PermissionMode`、`PermissionRule`、`RuleScope`、`PermissionEvaluator`，以及 `PermissionClassifier` 调用契约与其 `LlmPermissionClassifier` 实现。
- 包边界：`config` 是叶子包，只承载原始配置形态（字符串清单与布尔），不引用 `policy` 类型；规则定义、语法解析与匹配落在 `policy`——`PackageBoundaryTest` 的 `FORBIDDEN` 只禁止 `policy` 依赖 `agent` / `tool` / `hitl` / `runtime` 等上层，不禁止依赖 `config`；求值接线留在 `hitl` 的 `HitlToolRegistry`（现有 `ApprovalGate` 调用点）。分类器需要模型调用，不能落在 `policy`，只能由 `hitl` 侧持有并在第 10 阶段回调。
- 分类器引入非确定性：现有审批测试必须支持注入桩，不能依赖真实模型；同时新增「分类器不可用」「连续失败」两条失败路径的定向测试。
- 分类器的提示词与可见上下文成为新的维护面：提示词是独立资源文件（`src/main/resources/prompts/permission-classifier.md`），不内联在代码里；可见上下文由求值链显式构造最小集合，不复用会话消息。
- hooks 第 0 阶段保持只收紧，`HookDispatcher.Decision` 不扩展 `ALLOW`。
- 文档面是重写而非增量修改：`AGENTS.md`、`docs/agents-reference.md`、`README.md`、`TODO.md` 的授权章节都需要按新模型重新表述。
- 交互面新增：模式切换键位、状态栏模式显示位、权限面板、项目信任确认入口。
- 命令语义变化：`/grant` 从「授权下一轮」变为「写会话规则」；`/grant off` 的语义随之从「取消待执行授权」变为「清除会话规则」。
- CLI 表面变化：新增 `/mode`（唯一权限命令，`/hitl` 与 `/readonly` 删除）；状态栏的 `HITL: ON/OFF` 位替换为模式位。沙箱（`ISOLATED_PROJECT`）不新增开关——它由内部执行上下文施加。审批通道在有终端交互时始终可用：「要不要问」由模式决定，关掉通道会让本该询问的动作静默阻塞在 stdin，比直接拒绝更难排查。通道恒为可用之后，「活动轮次能否并发读终端」不能再沿用 HITL 开关判断——那会让条件恒为假、ReAct 轮次中的 `/now` 与 `/cancel` 静默失效；改由 `Main.neverPrompts` 按权限模式与规则集判断（`dontAsk` 收口为拒绝、`bypassPermissions` 且无显式 `ask` 规则）。
- 包边界约束：`policy` 不得依赖 `tool`（`PackageBoundaryTest` 的 `FORBIDDEN` 已机械验证），因此 `PermissionMode` 只声明抽象的能力上限与询问策略，模式到 `ToolAccessScope` 的映射落在 `cli` 的接线层，不能落进 `policy`。
- 规则层的资源值提取集中在 `ApprovalGate.resourceValues`：路径类返回项目相对键，无法解析时返回 `null` 而不是空清单——空清单会让不带 specifier 的规则意外命中。
- 规则次序严格照 WorkBuddy：`deny` → `allow` → `ask`，命中即短路，不做具体度比较。代价是宽泛的 `allow` 会吞掉更窄的 `ask`，由加载期告警提示，不靠改次序解决。`PermissionRule.literalPrefix()` 只服务于该告警，不参与任何判定。
- 规则解析失败整体降级为「无规则」并打印告警，不做部分接受：一条写错的拒绝规则被静默丢弃，用户会以为它在生效。
- 迁移期风险：现有测试大量断言 `TaskGrant` 的一轮语义与 `approvedAll` 的每轮清空，切换时需要同步重写这些断言，而不是让它们静默失效。

## 主机命令的规则层与模式层对齐

非隔离路径下 `execute_command` 会在 `applyHitl` 的第一行早退到 `reviewHostCommand`——`commandExecutesOnHost()` 在能力范围非 `ISOLATED_PROJECT` 时恒为真，而这是默认情形。这条早退**跳过了规则层与模式短路**，曾经导致 `deny execute_command(...)` 不生效、`dontAsk` 下主机命令不被收口为拒绝。

已修：`reviewHostCommand` 现在自己求值一次规则层与模式层，但**只吸收收紧方向的判定**。

| 判定 | 对主机命令是否生效 | 理由 |
| --- | --- | --- |
| `deny` 规则 | 生效 | 用户明确的拒绝意志，方向是收紧 |
| `dontAsk` 模式 | 生效（收口为拒绝） | 「不询问」与「必须单次确认」同向 |
| `ask` 规则 | 不适用 | 主机命令本来就必须审批 |
| `allow` 规则 | **不生效** | 方向是放宽，会绕过单次人工确认 |
| `bypassPermissions` | **不生效** | 同上 |

**为什么放宽类判定一律不参与。** 主机命令的单次人工确认在本项目里刻意不可被任何授权免除——任务授权、全部批准、参数修改都不行（`TODO.md` 2026-09-20 条目）。让 `allow` 或 `bypassPermissions` 生效，等于给这条硬要求开一个后门，而它正是被设计出来堵死后门的。这是**刻意比 WorkBuddy 更严**的一处：WorkBuddy 的 bypass 是全局的。

代价必须写清楚：`allow execute_command(...)` 规则在主机路径上写了不生效。加载期由 `Main.loadPermissionRules` 打印告警并给出替代做法（要拦命令请改用 `deny`）。这不是「规则静默失效」，而是「有提示、有理由的不生效」。

隔离路径（`ISOLATED_PROJECT`）不受影响：命令走沙箱后端，不经过 `reviewHostCommand`，规则层与模式层在 `applyHitl` 内正常求值。

**对 `auto` 的直接后果必须写清楚**：主机命令路径既不放宽也不询问分类器，因此 `auto` 在默认（非隔离）会话里**覆盖不到 `execute_command`**——它能自动放行的只有文件编辑类动作（`write_file` / `edit_file`，以及未被删除阈值拦下的 `delete_files`）。编码任务里命令调用占比不低，所以「自动审批」的实际覆盖面小于模式名给人的预期。

根因不是「主机命令天生该更严」，而是**缺沙箱层**。WorkBuddy 的 `bypassPermissions` 可以全局生效，是因为 Bash 子进程在 OS 层沙箱内运行，放宽的后果有边界兜住；DevCLI 的默认主机路径没有等价边界，只能拿「不可免除的单次确认」顶上。第 4 阶段若引入可靠的沙箱执行，这条限制才有条件解除；在那之前，把 `allow execute_command(...)` 或 `auto` 的作用范围讲成「命令也能自动放行」是失实的。

## 其余已知差距

**分类器自身的差距**：固定用当前主模型判定，没有按动作复杂度选择轻量模型；提示词没有版本管理。判定质量**已可度量**——`benchmarks/permission-classifier-evals/v1/cases.jsonl` 加 `PermissionClassifierDriver` 提供组件级定向诊断：自建对抗清单加合法请求对照，逃逸（期望拒绝却放行）与误拒（期望放行却拒绝）分开统计、外部失败单列、按 `default` / `isolated_only` 拆分可达性（见 `docs/permission-classifier-evals.md`）。仍未覆盖的是：多次重复运行的稳定性、按动作复杂度分层，以及 Agent 级（经完整求值链真实执行）的安全评测——后者仍属公开集合接入缺口。

**与 WorkBuddy 的差距**（需要单独排期，不阻塞第 3–5 阶段）：`Bash` 规则的 `*` 可跨 `/`（DevCLI 用 Java glob，不跨）；路径归一三层（`//path` / `~/path` / `/path`）；`mcp__server` 与 `mcp__server__*` 等价；`mcp__*` 仅在 `deny` / `ask` 生效；Skill 精确匹配；`PreToolUse` 钩子可返回 allow / ask（DevCLI 的 `HookDispatcher.Decision` 只有 `CONTINUE` / `WARN` / `BLOCK`，只能收紧）；`/permissions` 交互面板；`--allowedTools` / `--disallowedTools` 命令行参数；`permissions.trustedDirectories`；`disableBypassPermissionsMode`。
