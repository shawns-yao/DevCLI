# 架构决策记录（ADR）

## 这个目录是什么

每篇 ADR 记录**一次架构决策**：当时的背景、考虑过的替代方案、最终选择和它的后果。

**ADR 不是**架构合同、需求规范或未来规划，也不能单独作为「当前实现必须如何工作」的事实源。判断当前行为以源码、公共类型、测试和机械检查为准。ADR 与实现不一致时，先核实变更历史；确认记录已过时时，在**同一次变更**里修正它。

## 编号规则

**编号一经分配即冻结，不重排、不复用、不回填。**

新增时取当前最大编号 +1。不要为了「看起来整齐」给历史决策补编号——补写的记录没有当时的取舍语境，只会制造看起来权威但内容失真的文档。

## 什么时候写

需要写：

- 新增依赖、公共 API、协议、持久化格式、包边界或安全模型
- 引入新的架构模式，或改变现有架构行为
- 在两个都能工作的方案之间做了取舍，且这个取舍以后会有人质疑

不需要写：

- 局部实现细节、命名、格式偏好
- 单纯的缺陷修复（除非修复改变了架构契约）
- 只为假设中的未来需求预留的扩展点

## 格式

```markdown
# <一句话陈述这次决定了什么>

## 背景

什么问题必须解决，有哪些硬约束。

## 决定

最终选择是什么，以及它为什么成立。

## 关键取舍

逐一列出考虑过但没选的方案，写清各自会在什么条件下更好、为什么这次不选。

## 后果

这次决定带来什么代价和限制，哪些场景会因此变难。
```

「关键取舍」是全文最重要的部分。只写「决定了什么」而不写「放弃了什么」，读者无法判断这个决定在什么条件下应该被推翻。
