# 授权分层：把「持久基线」与「任务例外」分开

> **已被 [ADR 0006](0006-权限模型补齐规则层与模式层.md) 取代（2026-09-21）。**
>
> 本文决定的 `permissions.baseline` 与 `TaskGrant.merge` 均已从代码中移除：前者与规则层 `permissions.allow` 完全重叠，后者的并集语义造成「授权只能放宽、不能收紧」——正是 ADR 0006 要消除的方向性错误。
>
> 保留本文的目的只有一个：记录「在单层模型上叠加持久基线」这条路径为什么不够。它在错误的一层上打补丁，缺的是 deny 通道，不是更好的基线。判断当前行为请以 ADR 0006 与源码为准。

## 背景

当前系统里，用户能给出的两种放行都只作用于**一轮任务**：

- `TaskGrant`：`Main.java` 在每轮任务开始时取出 `nextTaskGrant` 赋给 `grantForTurn`，随即把 `nextTaskGrant` 重置为 `TaskGrant.NONE`。
- 任务级「全部放行」（审批框按 `a` 产生的 `approvedAll`）：每轮任务开始前调用 `hitlHandler.clearApprovedAll()`，注释写明「只在本轮任务内有效，不跨用户消息静默继承」。

设计者选择「一轮」的理由是成立的：**授权应当按任务意图给出，不应当静默跨越任务边界。** 用户在「清理旧代码」任务里授权 `src/**`，这个授权的语义是「清理旧代码需要写 src」；下一个「加新功能」的任务若自动继承它，用户可能根本不知道自己还处在授权状态。这是授权漂移。

但代价被低估了：**同类任务必须反复授权，且成本恒定不随时间下降。**

具体场景：用户分批重构，连续做 5 个都需要写 `src/**` 的任务。每个任务都要重新输入 `/grant write src/**`——这不是按一下键，是要重新构造路径参数。做第 50 个同类任务时，仍然要输入第 50 次。

同时暴露出两个附带缺口：

1. **粗粒度机制失去了它本该有的价值。** `approvedAll` 的存在意义是「懒得看了，别问了」，但它同样每轮重置，退化成「每轮按一次 `a`」。
2. **放行状态缺少可见性与撤销入口。** `/grant off` 只重置 `nextTaskGrant`，不清 `approvedAll`；同一轮内按过 `a` 之后没有任何命令可以撤销。也没有任何命令能列出「当前生效的全部放行」。

## 决定

引入**授权分层**，把授权拆成持久基线与任务例外两层。

### 基线：持久，用户级配置

在 `~/.devcli/config.json` 新增 `permissions` 段：

```json
{
  "permissions": {
    "baseline": {
      "writeGlobs": ["src/**"],
      "networkHosts": [],
      "projectCommands": true
    }
  }
}
```

基线**默认生效、跨会话持久**。它由用户通过 CLI 命令或编辑器维护；因为 `~/.devcli/config.json` 与项目级 `.devcli/config.json` 均在 `SensitivePathPolicy` 的 `AGENT_CONFIG_NAMES` 保护范围内，**Agent 的工具写路径无法修改它**——这一点是刻意保留的：授权配置不应由 Agent 自己改写。

### 例外：临时，任务级

保留现有 `TaskGrant` 与 `/grant` 语义（一轮有效），但它的含义从「唯一的授权来源」改为「叠加在基线之上的增量」：

```
本次任务的有效授权 = 基线 ∪ 本轮 /grant 例外
```

用户因此不再需要每轮重复基线部分，只在需要超出常态时给出例外。

### 撤销与可见性

- `/grant off` 的清除范围扩大：同时重置 `nextTaskGrant` 与 `approvedAll`。
- 新增 `/grant status`：列出三层当前状态——基线、本轮例外、会话放行缓存。
- 状态栏常驻显示基线摘要。

## 关键取舍

**为什么基线放用户级而不是项目级。** 项目级 `.devcli/config.json` 会随仓库分发。但授权的三个维度里只有 `writeGlobs` 是项目相对的，`networkHosts` 与 `projectCommands` 表达的是「用户信任哪些操作」，与具体仓库无关。把基线放用户级与这个语义一致。若后续确需项目级覆盖，可作为在基线之上的又一层增量，不改变本次分层结构。

**为什么不做「每轮提示复用上次授权」。** 那只是把「重新输入路径」降级为「按一次 y」，仍然是每轮一次交互，疲劳只是减轻而非消除。基线一次配置后永久生效，才真正解决问题。代价是用户要主动维护配置文件——但这与现有 `~/.devcli/config.json`（provider 配置）的维护方式一致，不引入新的心智负担。

**为什么保留 `TaskGrant` 的一轮语义，不改成会话级。** 基线与例外的分工是「基线管常态，例外管本次」。若例外也持久，两层就合并了，分层失去意义。「一轮」正是「这次任务需要超出常态的权限」的准确表达。

**为什么不引入分类器自动判定（如 WorkBuddy 的 `auto` 模式）。** 那是用模型判断替代人工审批，需要额外模型调用，并引入「用模型判断安全性」这一新的风险面。本次只做授权分层，不改变判定权威来源——`ApprovalGate` 的三值判定顺序与「策略拒绝不可被授权覆盖」全部保持不变。

**为什么状态栏显示基线是硬要求而非可选项。** 基线持久化后，用户容易忘记自己配过什么——这正是「授权漂移」的另一种形式。基线能被接受的前提是它始终可见。因此任何基线变更都必须即时反映到状态栏，这条约束与实现同时交付。

## 后果

- `TaskGrant` 的定位从「唯一授权来源」变为「例外层」。`ApprovalGate` 的判定逻辑本身不变，但它接收的授权对象需要改为「基线 ∪ 例外」的合并结果。
- `DevCliConfig` 需要扩展 `permissions` 段；新增 `TaskGrant` 的合并操作（复用现有 `withWriteGlobs` / `withNetworkHosts`）。
- `/grant` 命令语义扩展：新增 `status` 子命令，`off` 的清除范围扩大。命令帮助文本需要同步。
- 状态栏（`BottomStatusBar` / `statusInfo`）需要新增基线显示位。
- 授权可见性成为新的强约束：基线变更与状态栏显示之间不允许出现不一致窗口。
- **本次不做**：分类器自动判定、项目级基线覆盖、基线的时间或次数限制、`/grant` 的历史回滚。
- 行为变更需同步 `AGENTS.md`、`docs/agents-reference.md`、`README.md` 中的授权说明，以及 `TODO.md` 对应条目状态。
