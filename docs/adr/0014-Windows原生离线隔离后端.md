# Windows 原生离线隔离后端

## 背景

现有隔离工作区与 PatchSet 保护主项目归并，但主机命令白名单不能约束构建插件内部行为，本地 stdio MCP 也原本直接继承主进程环境。

## 决定

1. 新增显式 `WINDOWS_NATIVE` 命令后端。默认仍为 Docker；普通非隔离命令保持原审批路径，不自动改为沙箱执行。
2. 采用 AppContainer 空 capability 集与独立随机身份，限制网络；Job Object 限制 64 个进程和合计 1 GiB 提交内存，禁止 breakaway，启用 kill-on-close。目标先挂起创建、加入 Job 后恢复。
3. Java 通过受控 JSON 协议调用 .NET 8 自包含启动器。只传递目标命令、工作目录、读权限根、父进程标识和期限，不继承目标环境变量。句柄只继承三条标准流。
4. 每个进程会话只授权当前目录及宿主显式配置的运行时读权限根。临时文件与用户配置使用 AppContainer 专属目录，`.git` 显式拒绝；普通 AppContainer 仍能读取系统默认开放的资源，不宣称完整文件系统视图隔离。
5. 命令复用 `WorkspaceExecutionSession` 提供的目录。结束时先终止并确认 Job 内所有进程退出，再检查产物与回收 ACL；随后现有链路才创建 PatchSet、验证和归并。
6. 本地 MCP 按 server 显式配置 `sandbox: WINDOWS_NATIVE`，首版只读项目目录、禁止自定义 env，要求绝对 `.exe`。每个 server 使用独立身份，不自动变更工具信任或审批。该实例仍是项目级只读服务，不宣称 Worker 级上下文隔离，也不支持自动归并 MCP 写入。
7. 远程 HTTP MCP 不受本机隔离；配置原生沙箱时拒绝，而非给出虚假的隔离标记。MCP 初始化失败立即关闭已创建的 client/transport。
8. 保留现有单次主机审批，不因 `WINDOWS_NATIVE` 自动绕过；执行位置与隔离能力分别表达。创建失败不回退。

## 取舍与限制

- SRT 发布版 0.0.77 的 Windows 实现使用共享沙箱账户，且官方列出系统 DNS 未受围栏限制。未将其直接作为并行任务强隔离基础。
- 不创建系统账户，不安装机器级 WFP 规则，不需要提权安装。任务授权会临时修改指定目录 ACL；运行时目录必须由当前用户具备 ACL 管理权限。SYSTEM 所有的工具安装不自动提权处理，可由用户准备专用副本。
- 重解析点和硬链接在授权及收集前拒绝；不支持网络共享路径。对外部特权进程恶意并发改写路径、系统漏洞等没有完整防御保证。
- Java 父进程退出后，启动器主动终止 Job 并回收；启动器自身异常被强杀时由 kill-on-close 终止目标，但可能残留 profile/ACL/control 文件。身份不复用，尚未实现崩溃残留自动清扫。
- 不覆盖远程服务、宿主内置文件工具、浏览器控制或未经显式选择的 MCP；不等同于虚拟机，不防止授权目录内的错误业务修改。
- `.NET 8` 启动器需独立构建分发；Maven 构建不会自动下载 SDK 或生成原生包。

## 验证

定向测试包含实际 AppContainer 执行、工作区外读写拒绝、TCP 回环/公网及 DNS 请求样本、环境变量隔离、正常退出清理子进程、超时/取消、两个并发工作区互访拒绝、JDK 副本编译、本地 MCP 协议与只读访问，以及现有审批/工作区/PatchSet 入口链路。测试样本不构成普遍安全证明；默认 Maven 运行未配置启动器时会跳过真实 Windows 隔离用例。

运行方式见 [Windows 原生隔离说明](../windows-native-sandbox.md)。
