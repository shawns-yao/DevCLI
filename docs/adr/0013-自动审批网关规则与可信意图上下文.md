# 自动审批网关：四类规则与可信意图上下文

## 背景

原审批链使用 `deny` / `ask` / `allow` 三类规则，并把完整对话历史交给分类器。两个问题由此产生：

- 宽泛 `allow` 可能吞掉更窄的人工确认边界；
- Assistant 自述、工具结果和委派内容进入分类器后，可能被误当成用户授权证据。

## 决定

1. 配置只保留 `hard_deny` / `soft_deny` / `allow` / `environment`，不读取旧键，不保留兼容入口。
2. 策略硬边界和 `hard_deny` 始终确定性拒绝；删除、回滚、浏览器与 MCP 逐次审批仍必须由人确认。
3. `auto` 模式不让 `allow`、`soft_deny`、任务授权提前短路，而是把四类规则注入分类器一次判定。
4. 非 `auto` 模式按 `hard_deny` → `soft_deny` → `allow` 求值；无法判断用户意图时，显式边界优先。
5. 分类器只接收真实用户消息和 Assistant 已发起的结构化工具调用。Assistant 自述、工具结果、
   系统注入、插件内容和委派报告在进入模型前删除。
6. 规则类别分别注入系统提示词的固定位置；缺失任一占位符时装配失败，分类器调用失败时继续失败关闭。

## 后果

- 旧配置键 `deny` / `ask` 不再生效，用户必须显式迁移。
- `auto` 中的宽泛授权不再绕过分类器；自动审批更可审计，但会增加分类器调用次数。
- 原 `ClassifierTranscript`、覆盖告警启发式和 `PermissionRule.literalPrefix()` 删除，不维护两套语义。
