# 记忆存储的权威边界：Markdown 是唯一权威，SQLite 降级为纯缓存

> **已被 [0007](0007-长期记忆对齐-workbuddy.md) 取代（2026-09-21）**：
> 「Markdown 是唯一权威」仍然成立，但当前已改为全局/项目物理隔离的主题文件，
> `MEMORY.md` 仅为可重建派生索引。SQLite 索引、旁路计数、审核证据和晋升/确认队列已移除。
> 当前行为以 ADR 0007 与源码为准；本文只保留当时的决策语境。

## 背景

长期记忆采用 Markdown + SQLite 双存储。设计文档声称「Markdown 决定正文内容，SQLite 决定运行时状态和定位，不对同一字段形成双重权威」。**实测发现这个声称与实际实现不符。**

2026-09-19 对本机 `~/.devcli/memory/` 的实测（51 条记忆）：

| 事实 | 数据 |
| --- | --- |
| 记忆目录 | `~/.devcli/memory/`，**不在任何 git 仓库内** |
| Markdown 卡格式 | frontmatter（`devcli-memory-format` + `payload` JSON）+ `# <id>` + `## Content` + `## Evidence` |
| `memory_facts` 列数 | 29 |
| `content` 列填充率 | **0/51**（正文确已迁出） |
| `confidence` / `review_state` / `conflicts_with_json` | **51/51**，且 Markdown payload 里也有同名数据 |
| `revision` | **51/51 全是 1**（修订机制从未启用） |
| `superseded_by` / `subject` | **0/51**（死字段） |
| `index_state` | **51/51 全是 `PENDING_INDEX`**（索引从未成功建立） |
| `memory_vectors` 行数 | **2**（51 条记忆） |

**双权威确实存在，但不在设计文档指出的字段上，而在审核类字段上**：`confidence` / `reviewState` / `conflictsWith` 同时存在于 Markdown payload 与 SQLite 列。

代码层面已经有一半是 Markdown 权威：`SqliteLongTermMemoryStore#parseRow` 在 `hydrate=true` 时先读 SQLite 列，**紧接着用 Markdown 文档的值整体覆盖** `content` 与整个 `evidence`。SQLite 那几列只在 `hydrate=false`（轻量 Catalog）路径下才真正被消费。

## 决定

**Markdown 是记忆的唯一权威数据源。SQLite 降级为纯缓存**，只承担两件 Markdown 做不了的事：

1. **派生索引的载体**：倒排与向量必须落盘，否则每次启动重算。
2. **机器高频累积的计数**：`recall_count`、`validated_use_count`、`last_recalled_at_ms`、`last_validated_at_ms`。这些每次召回都会变，写进 frontmatter 会把文件版本历史刷爆。

边界用一条线划：**人类需要看或改的内容归 Markdown；机器高频读写、且可由 Markdown 重建的归 SQLite。**

按这条线，字段归属调整为：

| 内容 | 归属 | 当前状态 |
| --- | --- | --- |
| 正文、证据、`confidence`、`reviewState`、`conflictsWith` | Markdown | 已双存，需去掉 SQLite 侧 |
| 修订历史 | Markdown（追加修订） | SQLite 有 `revision`，Markdown 无 |
| 倒排 / 向量 | SQLite | 已对 |
| 召回 / 验证计数 | SQLite | 已对 |
| ID→路径定位（`markdown_path`） | 可去除 | 路径可由 ID 派生或扫描获得 |
| `index_state` 状态机 | 可退化 | 见下 |

## 关键取舍

**直接删除 SQLite 的审核类列。** 不成立，有两个约束。

其一，`LongTermMemory:241` 用 `getEvidence().reviewState() == REJECTED` 做写路径守卫，`:382` 用它判断 no-op；这两处读的是 `entries` 里的**轻量 Catalog 条目**，而轻量条目正是不 hydrate 的那批。删列会让轻量 Catalog 的 `reviewState` 退化为默认值，守卫静默失效。

其二，`migrateLegacyBodies` 依赖 `markdown_path` 为空的历史行从 SQLite 列读正文与证据。**这几列在遗留库升级路径上仍然必要**，因此本次不删除 schema 列，只停止为有 Markdown 源的行写入副本。

**「只读 frontmatter 就能拿到元数据」这个设想在当前格式下做不到。** payload 把完整正文嵌在同一个 JSON 里（`{"id","content","confidence",...}`），元数据与正文无法分离读取——要拿 `confidence` 就必须读完整行。真正的解法是把元数据拆成独立 frontmatter 字段、正文留在 body，但那要改磁盘格式并迁移现有文件，属于独立变更，本次不做。

**当前实现的代价是：轻量 Catalog 会读全部 Markdown 正文。** 51 条量级无感知；万条量级需要先做上面那个格式拆分，或退回 mtime 失效检查。

**保留双写，只把读路径统一到 Markdown。** 否决。双写意味着两处都可能成为真相，任何一次写入失败都会留下不一致；而且写的那份在 hydrate 路径下永远被覆盖，是纯浪费。**冗余写入不是「多一层保险」，是「多一层需要维护的一致性」。**

**把审核类字段留在 SQLite、让 Markdown 只存正文。** 否决。`confidence` / `reviewState` / `conflictsWith` 是**人对记忆的判断**，不是机器状态。人对某样东西的判断必须落在人能看能改的地方；放 SQLite 会导致「人工编辑 Markdown 后状态不生效」，设计文档为此不得不引入文件监听器 + 导入作业 + 冲突流水线——**那是在为一个自己制造的问题打补丁**。

**立即 DROP COLUMN 完成迁移。** 否决。SQLite 的 `DROP COLUMN` 需要 3.35+，且现有 51 行数据需要迁移窗口。更稳的路径是**先停止写入与读取，列留在表里无害**；等确认无回归后再用「重建表」的方式清理。删除列不带来任何行为收益，不应与行为变更同时进行。

**把 SQLite 做成「可随时 rm 重建」。** 部分成立。索引部分确实可重建；**计数部分不可重建**（历史累积，删了就没了）。因此「纯缓存」这个说法要限定为「索引层可重建、计数层有损」。若真要 rm 重建，需要先决定计数是否接受归零。

**为未来规模预付索引复杂度。** 保留但标注。51 条记忆、向量索引 2 行、全量重建小于一秒。当前的 outbox、两阶段状态机、启动对账**从未完成过一次完整周期**——代价已付、收益未到。这不必然是错的，但应明确知道预付款对应的是哪个规模。

## 本次实施范围

已实施（对应 ADR 的「决定」部分）：

- `SqliteLongTermMemoryStore#parseRow`：**有 Markdown 源的行一律从 Markdown 取正文与全部证据字段**（`hydrate=false` 时只丢弃正文与证据原文，保留排序与守卫需要的字段）；`markdown_path` 为空的历史行仍从 SQLite 列读，供 `migrateLegacyBodies` 迁出。
- `SqliteLongTermMemoryStore#executeUpsert`：**停止写入** `confidence` / `source_quote` / `evidence_reasoning` / `review_state` / `conflicts_with_json` 五列。新行不再产生副本。

未实施（有意留下）：

- **schema 列不删除**。遗留库升级路径仍需要它们；删列没有行为收益，只承担迁移风险。
- **Markdown 格式拆分**（元数据独立成 frontmatter 字段、正文留 body）。这是消除「轻量 Catalog 必须读全文」的唯一办法，但要迁移现有文件，属独立变更。
- **持久性方案**（记忆是否纳入版本控制或备份）。本 ADR 只划逻辑边界。

## 后果

- 写记忆变成「原子替换一个 Markdown 文件」，跨存储原子性问题自然消失；对账、outbox、`PENDING_MD` 两阶段状态机随之失去存在理由。
- 人工编辑 Markdown 直接生效，导入作业退化为普通的重建触发。
- **轻量 Catalog 的启动成本从「只读 SQLite」变成「读 N 个 Markdown 的 frontmatter」**。51 条量级无感知；到万条量级需要重新评估，届时可退回「frontmatter 单独缓存」。
- **持久性问题本次未解决，且它比双权威更根本**：记忆在 `~/.devcli/memory/`，不在版本库内，Markdown 与 SQLite 同盘同目录、都是单副本。Markdown 成为唯一权威之后，**删错一个文件就是永久丢失**。本 ADR 只划逻辑边界，不解决物理持久性；需要单独决策「记忆是否纳入版本控制或备份」。
- 修订历史归属 Markdown 之后，SQLite 的 `revision` / `superseded_by` 成为可推导字段，可随审核类列一并清理。
