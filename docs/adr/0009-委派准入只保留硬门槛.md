# 委派准入只保留硬门槛，收益评估降级为决策辅助

> **准入范围已被 [ADR 0010](0010-委派程序侧准入对齐参照实现.md) 修订（2026-09-22）。**
>
> 本文「决定」第 1 条列举的六条硬门槛中，契约字段完整性（inputs、scope、done_condition、deliverable）与 Worker 写入范围已归入工具 schema 与语义校验层，以参数错误返回而非策略拒绝；「不频繁依赖父状态」判据连同其字段一并移除。准入层现只保留自述式执行粒度判据，并新增单会话派出量配额。
>
> 本文其余结论继续有效：收益评估降级为诊断且不回灌模型、唯一滥用硬规则是自述式判据、拒绝文案必须确定性可操作、「值不值得」下沉为提示词软策略。
>
> 判断当前行为请以 ADR 0010 与源码为准。

## 背景

默认 ReAct 路径允许主 Agent 按需调用 `delegate_task`。该调用先经过 `DelegationPolicy`，其判定由一个收益成本公式给出：收益为固定底数加写入范围隔离度，成本为固定底数加传递开销，两者差值达到配置阈值才放行，否则以 `POLICY_DENIED` 拒绝。

这套公式把「值不值得委派」做成了执行层硬拒绝条件，带来三个问题。

**一、制造了参照实现没有的失败模式。** 腾讯 CodeBuddy Code 与 Claude Code 的委派入口都只做资源配额（嵌套深度、单会话派出量）与「说明书」式适用场景声明，均不评估任务本身是否划算。DevCLI 的收益公式在两者中都找不到对应物，属于自创机制，因此也没有外部行为可以对齐验证。它新增的失败模式是：任务本应委派，却因算分不足被硬拒。

**二、拒绝理由不可操作。** 「委派收益不足，应由主 Agent 执行」对模型没有可执行的下一步——模型无法把任务改得「更值得委派」，除非修改声明本身。若在提示中说明「把写入范围写窄、背景写短就能通过」，拒绝理由会直接诱导「为过门槛而优化声明」，而任务本身并未变得更适合委派。这比不拒绝更糟。

**三、数值关系与设计注释的意图不符。** 只读角色不声明写入范围，隔离度取中性值，收益因此恒为固定值；成本只需保持最低档即可放行。结果是三个只读角色的准入几乎不构成筛选，实际压力全部落在 Worker 的写入范围声明上。公式宣称筛选「任务被隔离得多干净」，实际筛的是「声明写得漂不漂亮」。

同时，委派报告信任边界（ADR 0008）已确立报告为不可信数据。本次改动不触及该边界，也不改变「保留按需委派、不引入纯协调模式」这一决定。

## 决定

1. **委派判定拆成两层，职责分离。**

   **硬门槛——决定是否放行**，全部是「能不能干」而非「划不划算」：
   - 结构化任务声明必须是合法 JSON 对象；
   - 声明的执行粒度必须自述为需要多轮 Agent 循环；
   - 声明必须写明不频繁依赖父 Agent 的中间状态；
   - 输入、范围、完成条件三项必须为非空文本；
   - 必须提供非空交付物；
   - Worker 必须声明非空写入范围。

   契约完整性属于硬门槛，不降级为「基本完整」。子 Agent 不继承父会话历史、不自动召回记忆、看不到兄弟消息，契约不全时它只能靠猜，这是能力缺失而非效益不足。

2. **收益评估降级为诊断字段。** 契约闭合、作用面隔离、传递成本三个维度保留，继续产出收益、协调成本、分数与建议文本，但只写入运行事件，不参与放行判定，也不回灌给模型。分数不作为模型可见的反馈。

3. **收益阈值配置项语义变更。** 原准入门槛改为低收益告警线，仅影响事件中的低收益标记与建议文本。键名同步改为表达告警语义，旧键不再读取。

4. **「值不值得」下沉为提示词软策略。** 在 `delegate_task` 工具说明与主 Agent 模式提示词中写入可对照的判断条件，不使用「范围越窄越好」「背景越短越好」这类无法自比的相对表述。

5. **唯一保留的滥用硬规则是自述式判据。** 即第 1 条中的执行粒度声明：模型自己声明该任务为单次工具操作时拒绝。不新增按工具名、按文件数或按输入长度推断「明显滥用」的规则清单。

6. **拒绝文案必须确定性且可操作。** 只保留硬门槛拒绝，理由指向模型可立即执行的下一步；不再出现「收益不足」这类无法据此调整的表述。

## 关键取舍

### 不新增嵌套深度上限与单会话子 Agent 数量上限

参照实现用「深度上限加派出量上限」防失控，DevCLI 已有等价或更严的约束：子 Agent 被明确禁止再次委派，深度恒为 1，比任何数值上限都严；总量由父子共享的 Token、轮数与工具调用额度控制，新增独立计数器会形成第二套总量机制，与「一个开关不承担两个语义」「避免隐形第二套机制」的既有结论冲突。若将来放开递归委派，深度上限必须与递归开关在同一次变更中引入，不能只放开不限制。

### 不把诊断分数回灌模型

回灌即诱导刷分。模型看到「本次收益低于告警线」后能采取的唯一行动是修改声明措辞，而声明改动不影响任务实质。只写事件则零刷分风险，同时保留事后统计「低收益委派占比及其最终成功率」的能力。代价是该分数对运行时行为完全没有影响——这正是「降级为辅助」的题中之义。

### 不用推断式规则判「明显滥用」

「只读一个文件」「只跑一个命令」这类判据是收益模型的极端取值，仍会误伤：单个文件可能是大体积日志或生成代码。自述式判据（模型自己声明执行粒度）同时免疫误伤与刷分——把「单次操作」改写成「循环」确实能通过门槛，但那等于模型承诺该任务需要多轮迭代，后续跑不出成果由它自己承担。既有实现已具备该判据，本次只需把它确立为唯一的滥用规则。

### 保留三个维度而不是整体删除

三个维度确实能描述一次委派是否划算，作为诊断指标有价值；有风险的是把近似模型当硬判定用。删除会同时丢掉「委派决策质量」这一可观测性来源，而保留的成本仅为一次事件写入。

### 不把软策略写成相对表述

参照实现的适用场景声明是可对照的量化条件，模型能直接比对自己的任务。相对表述无法自比，等于没有约束力。

## 后果

- 低收益委派会被真正执行。抑制浪费的责任从程序硬判转移到提示词软策略，模型不遵守时不再有兜底。这是本决定接受的代价。
- 委派事件新增收益诊断字段与低收益标记；原「是否放行」字段只反映硬门槛。
- 旧收益阈值配置键不再读取，其值静默失效；文档与配置示例同步更新。
- 既有测试中断言「低收益被拒」的用例必须改为断言「低收益仍放行且被标记」，否则会掩盖新契约。
- 提示词软策略无法机械验证，只能靠评测观察委派频率与成功率；本决定不引入自动化的委派质量门禁。
- 契约完整性仍可能因模型漏填而拒绝，该路径的拒绝文案必须说明缺哪一项，不得笼统表述。
