# 委派程序侧准入对齐参照实现：结构校验归位、语义判据移除、新增单会话配额

## 背景

ADR 0009 把收益评估从准入判定降级为诊断字段，但程序侧仍保留六条硬门槛。把参照实现的程序侧准入逐条读出来之后，构成完全不同。

**Claude Code 的委派入口只有六条校验，全部是能力或结构约束**：团队功能在当前套餐是否可用、队友不能再派队友、进程内队友不能派后台代理、分叉子代理内不能再分叉、代理类型是否被权限规则拒绝或根本不存在、该代理必需的 MCP 服务是否可用。没有一条判断任务本身。

**CodeBuddy Code 只有两条纯配额**：嵌套深度到 5 拒绝、单会话派出量到 200 拒绝。

差异的根源是**继承语义**。Claude Code 的分叉子代理继承父代理的完整对话上下文与系统提示，子代理自己能看到全部背景，契约写得含糊也不影响它开工。DevCLI 的子代理只拿到显式传入的内容，不继承父会话历史、不自动召回记忆、看不到兄弟消息——契约是唯一的信息通道。

因此「不校验契约」不能直接照搬。可以对齐的是**校验的分层位置**：参数结构与运行时必需输入属于工具调用契约，留在程序侧；任务值不值得、耦合度高不高属于语义判断，交给模型。

同时发现一处真实缺口：参照实现都有单会话派出量上限，DevCLI 完全没有。ADR 0009 曾把「深度上限」与「数量上限」打包否决，理由写的是「深度恒为 1，新增计数器会形成第二套总量机制」。该理由对深度成立，对数量不成立——两件事被捆在一起否决了。

## 决定

1. **参数结构校验从准入判定层移到工具语义校验层。** 输入、范围、完成条件、交付物、Worker 写入范围的「非空」判定，性质是工具调用契约的结构校验，与参照实现的 schema 校验同类。它们不再以「未通过硬门槛」的形式拒绝，而以参数错误的形式返回，错误码与文案同步改变。

2. **移除纯语义判据「不频繁依赖父 Agent 中间状态」。** 这条判断的是任务耦合度，不是子代理能否开工。耦合度高的任务委派出去会跑偏，那是模型判断失误的代价，不是程序应当拦截的能力缺失。

3. **从工具契约中移除父状态依赖字段。** 该字段的唯一消费方是第 2 条判据，移除判据后字段没有读取方。继续保留会让模型填写一个无人消费的字段。

4. **保留自述式执行粒度判据。** 模型自己声明该任务为单次工具操作时拒绝。这是 ADR 0009 确立的唯一滥用硬规则，本次不变。

5. **保留 Worker 写入范围的结构校验。** 该字段是隔离工作区与运行时写入租约的必要输入，缺失会导致运行时无法建立边界。它属于「运行时需要它才能工作」，不是准入判据，因此随第 1 条一并归入结构校验层。

6. **新增单会话派出量配额。** 默认 200，与参照实现同量级，可通过配置覆盖。达到上限时拒绝后续委派，文案必须给出可执行替代路径。

## 关键取舍

### 为什么配额按会话计而不是按单轮计

DevCLI 的 Token 与轮数预算按单轮创建，委派会话对象也按单轮创建。若配额按单轮计，200 次上限在单轮内不可能触及，配额形同虚设。会话级计数器挂在 Agent 实例上，与该实例的工作记忆、会话标识同生命周期，语义与参照实现的「单会话」一致。

### 为什么配额上限取参照实现的量级

单次委派轮数上限为 32，200 次委派的理论上限远超父子共享 Token 预算能支撑的规模，因此该配额不承担实际限流。它的作用是兜底：让「委派是有限资源」在耗尽时以可操作的拒绝（由主 Agent 接手）收口，而不是静默地无限委派。

有两点必须说清，否则这个数字会被误读：

- **模型看不到剩余额度。** 配额只在被拒时以拒绝文案的形式被感知，不是事前约束，因此它不构成对模型行为的日常引导，只承担异常收口。
- **该上限按 Agent 实例（即一次 CLI 进程会话）累计，跨用户轮次不重置。** Agent 在 CLI 启动时创建一次并复用，一个长会话处理数十个任务后确实可能触达 200——**它不是「几乎不会触发」的虚设数字，把它当虚设是错的**。触达后的恢复途径是重启进程；runtime API 路径下的会话重置会重建 Agent，该路径不受此限制。

这与 ADR 0009「不新增第二套总量机制」的顾虑不冲突：该顾虑针对的是为已受限维度重复设限，而派出次数此前完全没有约束。

### 为什么不直接照搬「不校验契约」

参照实现可以不校验，前提是子代理继承完整上下文。DevCLI 的子代理不继承，契约是唯一信息通道。要照搬这条，前提是先实现上下文继承，那与现有隔离设计直接冲突，需要单独立项。

### 为什么结构校验不留在准入判定层

留在准入层会让同一类问题（字段缺失）以「策略拒绝」的形式出现，模型无法区分「我的参数写错了」和「这个任务不该委派」。前者模型能自己修，后者只能改由自己完成。分开之后，错误码本身携带了下一步动作。

### 为什么不保留父状态依赖字段作为软提示

字段留在契约里、但不做任何判定，等于让模型填写一个没有消费方的属性：既增加每次委派的声明成本，又会让模型误以为它会影响准入。耦合度判断改为写在工具说明里，作为模型自查条件。

## 后果

- 契约缺项从策略拒绝变为参数错误，既有测试中断言「缺字段被策略拒绝」的用例必须同步调整。
- 移除父状态依赖字段后工具契约变短；代价是耦合度高的委派请求不再有任何程序侧提示，只能靠模型自查与提示词约束。
- 单会话配额达到上限后拒绝后续委派，该路径的拒绝文案必须说明替代路径（由主 Agent 直接完成）。
- **该配额按进程会话累计且不可中途重置**：长会话触达上限后，剩余任务只能由主 Agent 直接完成或重启进程。若这个代价不可接受，正确做法是引入会话级重置点，而不是单纯调大数字——调大只是把问题推远。
- 该配额是否「合理」无法机械验证，只能通过评测观察触发频率。若长期从未触发，说明它只是信号而非真实约束——这个结论应当被记录下来，而不是继续保留一个看起来在防失控的数字。
- 委派准入层此后只剩一条语义判据。若将来该判据也被移除，准入层将只剩配额，届时应当重新评估这一层的存在意义。
