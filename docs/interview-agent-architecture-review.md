# DevCLI Agent 架构面试说明

完整逐题回答以及“当前实现 / 生产化改造”对照见 `docs/interview-agent-current-vs-production-qa.md`。

## 一句话定位

DevCLI 是面向软件开发任务的 Java Agent CLI。默认使用 ReAct 处理短任务；用户显式选择 `/plan` 时，系统先形成可校验计划，再按 DAG 调度、隔离执行、审查和提交。

## 为什么做这个项目

开发任务不只是问答。它会读取真实仓库、修改多个文件、运行命令，并且可能在中途失败。单次模型回答无法提供任务级状态、依赖调度、并发冲突控制、可恢复执行和可验证验收。

项目的核心目标不是让模型“多思考”，而是把模型的不确定性放进确定性的工程边界：模型负责理解、拆解和生成候选方案；程序负责校验、权限、调度、证据、提交和恢复。

## 整体架构

顶层有两条显式路径：

- ReAct：默认入口，适合目标明确、依赖少、反馈链短的任务。
- Plan：`/plan`，固定使用 Planner、Worker、Reviewer、隔离工作区和 checkpoint，适合多步骤、跨模块、高风险或可并行任务。节点是否并行由 DAG 与资源冲突决定，不需要第二个模式入口。

两条路径共享 `AgentExecutionEngine`、`ToolRegistry`、Memory 和运行事件。Plan 使用 `ExecutionGraph`、波次执行器、角色隔离、Pre-Review、Reviewer、PatchSet 和恢复拓扑。

Planner 负责形成 DAG 和验收标准；Worker 只负责节点实现；Reviewer 在硬检查之后根据真实产物和逐条验收结果决定是否通过。

## 为什么不是一直使用 ReAct

这不是 ReAct 架构错误，也不是靠修改提示词或增加记忆就能完全解决的问题。

ReAct 的决策单位是“下一步动作”。它擅长局部闭环，但缺少任务级承诺：没有稳定的全局依赖图、独立节点状态、并发边界、失败传播关系和恢复坐标。提示词可以提醒模型先规划，却不能把自然语言承诺变成调度器可检查的状态；记忆能补充历史事实，也不能替代依赖关系和事务边界。

因此 DevCLI 不自动猜测是否升级，而由用户显式选择 Plan。短任务使用 ReAct，避免 Planner 和 Reviewer 的时间及 Token 开销；跨模块、可并行、需要恢复或严格验收的任务使用 Plan。

## 输入到输出的完整数据流

1. CLI 解析用户输入，明确选择 ReAct 或 Plan。
2. Plan Planner 输出结构化计划：任务摘要、步骤、依赖和验收标准。
3. 程序提取 JSON，校验字段、缺失依赖、环、阻塞性空工作区检查和验收可判定性；失败时携带具体原因有界修复。
4. 确定性预检通过后，独立计划 Reviewer 对照原始目标检查需求、节点和验收标准的覆盖；拒绝则退回 Planner 有界修订，协议错误失败关闭。
5. 机器评审通过后展示计划和验收方式。用户可以执行、补充后重规划或取消；无交互环境遇到人工验收时失败关闭。
6. `ExecutionGraph` 计算就绪节点；资源冲突步骤分波，无冲突步骤进入有界并行 Worker。
7. 副作用步骤在隔离工作区执行。工具调用经过参数 Schema、权限、策略、HITL、审计和资源租约检查。
8. Worker 的文字声明不是完成证据。文件、代码和命令任务必须产生成功工具结果；否则触发一次强制执行协议，仍无证据则失败。
9. Pre-Review 先运行 Java 编译等确定性硬检查；失败直接打回 Worker，不调用产物 Reviewer。
10. 产物 Reviewer 读取隔离产物和工具证据，返回严格 JSON、三项评分以及每条标准的 `criteria_results`。
11. Reviewer 通过后生成 PatchSet。提交器先做全量哈希冲突预检，再原子应用；中途失败则按备份回滚并报告未恢复路径。
12. 步骤终态、产物、重试次数和恢复元数据写入 checkpoint；全部完成后删除 checkpoint，形成最终摘要和未完成的人工验收义务。

## DAG 是怎么生成和约束的

DAG 由 Planner 模型生成，但系统不直接信任。

每个节点至少包含：

- `id`：稳定节点标识。
- `description`：可执行的任务描述。
- `type`：分析、写文件、命令或集成等执行类型。
- `dependencies`：前置节点 ID 列表。

计划还必须包含全局 `acceptance_criteria`。每条标准至少包含：

- 必填的 `id`、`description`；可选的 `category`、`severity`。
- `test_signal`：什么结果算满足。
- `verification_method`：`TOOL` 或 `HUMAN`。
- `verifier`：自动验证工具名，或具体人工检查动作。
- `applies_to`：负责满足该标准的 DAG 节点，可使用 `FINAL` 表示全局集成义务。

程序先保留 Planner 原始 ID，再统一规范为 `step_N`，同时重写依赖和验收目标。执行前会拒绝重复 ID、缺失依赖、环、空目标和不存在的验收目标。普通节点只看到直接绑定的标准，避免无关标准污染局部审查；Final integration 再检查完整标准集合。Planner 输出无法解析、图无效或验收标准不可执行时，不会带病开工，而是清空 Planner 历史并携带失败原因重新生成；修复次数有上限。

## 双轨验收与语义偏航

“编译通过”只能证明代码在局部语法和类型层面成立，不能证明实现符合用户原始意图。因此验收采用双轨设计：

- `TOOL`：能够由真实工具产生证据，例如读取产物、编译或运行测试。
- `HUMAN`：涉及视觉、产品取舍、主观质量或无法稳定自动判定的标准，必须明确列为人工义务。

没有验证方式、没有判定信号、自动工具不存在，或把写入工具当验证器，都会在执行前被拦截。这样 Planner 不只是描述“要什么”，还必须回答“如何证明”。

执行前先由程序拦截不可执行标准，再由计划 Reviewer 检查需求覆盖和边界，之后由用户拍板；执行中产物 Reviewer 负责节点质量；最终集成节点重新对照原始任务检查入口、默认参数和跨模块联动。四道检查分别降低不可判定、计划偏航、局部实现偏航和集成偏航。

如果 Reviewer 也被误导，最终兜底不是另一个模型的主观判断，而是证据绑定：Reviewer 声称某条 TOOL 标准通过时，该标准声明的验证器必须出现在本轮真实成功工具调用中；实际执行的 Pre-Review 命令可作为 `execute_command` 证据。文字中的“已经测试”不算证据，调用了其他工具也不能替代指定验证器。再结合隐藏测试、隔离提交边界和人工验收，降低 Reviewer 与 Worker 共同偏航的风险。自然语言原始意图能否被完整转化为标准仍不是数学保证，关键业务仍需要人工确认或外部隐藏验证器。

## 失败、重试和回滚

失败先分类，再决定动作：

- LLM 限流、过载、超时、网络和服务端错误：Provider 层指数退避有界重试；流式内容开始后不重试，避免重复副作用。
- 工具参数或可纠正执行错误：把结构化错误返回同一 Worker 修正。
- Reviewer 不通过：原节点携带失败原因重做，Reviewer 轮数和节点重做次数都有限。
- 依赖节点失败：普通后继不执行；普通失败比例达到 50% 时 Final integration 熔断。
- 进程崩溃：通过 checkpoint 恢复原 DAG、Worker 绑定、已完成产物和剩余重做额度。
- PatchSet 应用失败：使用写前哈希和原文件备份回滚；回滚不完整时停止恢复，避免继续扩大损坏。

当 Reviewer 重试和原位重做全部结束后，系统不静默失败，也不让模型自动改写整张 DAG。最终结果会列出失败节点、两类已消耗额度、最后失败原因、保留的 checkpoint ID，并明确升级到人工介入：补充验收约束后重新规划，或人工修复后重新发起 Team。

不建议对所有失败使用级联回滚。已经完成且产物可复用的独立节点应该保留，否则会扩大故障面和成本。只有当上游结果已经写入主项目、下游失败破坏整体不变量，而且存在可靠逆操作时，才执行补偿式级联回滚。DevCLI 的本地文件修改通过隔离工作区和 PatchSet 延迟提交，优先从设计上减少级联回滚需求；外部支付、消息等副作用目前不承诺通用事务回滚，需要业务侧幂等键和 Saga 补偿。

## ReAct 失败后为什么不能自动切 Plan

一个典型失败是：ReAct 在多模块任务里连续解决局部错误，却漏掉默认入口或跨模块补偿。系统可以识别停滞、重复工具错误或预算耗尽，但这些信号不能可靠证明“改用 Plan 一定正确”，自动切换还会改变成本、权限和提交语义。

因此当前设计是显式模式选择，而不是失败后静默升级。失败结果可以作为重新发起 Plan 的上下文，但切换由用户确认。面试中应说明：我们解决的是执行结构问题，不把所有失败都归因于 ReAct，也不通过隐藏的自动路由掩盖成本变化。

## Reviewer 如何避免与 Worker 死循环

Reviewer 输入包含原始任务、当前节点、验收标准、Worker 结果和真实工具证据。输出必须是可解析 JSON，并包含功能正确性、集成完整性、代码质量评分以及逐条验收结果。

防循环措施包括：

- 确定性 Pre-Review 先拦编译错误，减少模型争论。
- Reviewer 输出结构化失败原因，而不是一句泛化评价。
- TOOL 标准必须绑定本轮真实成功的指定验证器，模型自述不能通过。
- Reviewer 轮数和节点重做次数分别有硬上限。
- 重做保持原节点 ID 和依赖，不创建无限增长的新分支。
- 达到上限后保持失败终态并输出人工升级信息；只有硬检查确实执行并通过时，部分可重试 Reviewer 故障才允许受限降级。

当前 `issues` 已结构化为列表并关联验收项，但还没有强制每个问题都携带文件、行号、期望值和实际值。这是后续可以继续增强的协议字段。

## 性能和实验怎么回答

旧订单履约 Saga 已退役，不再作为架构效果证据。正式实验应使用同一公开 SWE-bench Issue 配对比较 ReAct 与 `/plan`，并同时记录官方 resolved、Token、耗时、工具调用和失败类型。

## 面试回答主线

可以按以下顺序回答：

1. 先讲目标：把模型的不确定输出放入可校验、可恢复的工程管线。
2. 再讲模式边界：ReAct 处理短闭环，Plan 处理任务级依赖，Team 增加角色隔离和质量门禁。
3. 再讲数据流：计划、图校验、执行前评审、DAG 调度、隔离执行、硬检查、Reviewer、PatchSet、checkpoint。
4. 强调不信任原则：不信模型自述，只认工具结果、硬检查、哈希和人工确认。
5. 最后讲取舍：正确率提升伴随时间和 Token 成本；级联回滚只用于有事务边界且可补偿的副作用。

## 当前边界

- 计划模式由用户显式选择，尚未实现可靠的 ReAct 失败自动升级。
- 全局自然语言意图到验收标准的转换仍由 Planner 完成，无法消除遗漏，只能通过前置评审、最终集成、隐藏测试和人工标准降低风险。
- 自动标准声明具体验证工具并核对真实调用；复杂验证参数仍由 Reviewer 根据上下文选择。
- 本地文件具备隔离提交和恢复；外部系统副作用没有通用分布式事务保证。
- Saga 数据目前只有单次有效对照，需扩大样本和重复次数。
