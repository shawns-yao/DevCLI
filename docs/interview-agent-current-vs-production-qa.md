# DevCLI Agent 面试追问：当前实现与生产化演进

这份文档用于回答项目深挖问题。每道题都分成两层：先讲 DevCLI 当前已经实现的机制，再讲如果作为生产系统还需要补什么。生产化部分是演进建议，不代表当前已经交付。

## 当前状态速览

| 能力 | 当前状态 | 说明 |
| --- | --- | --- |
| DAG 缺失依赖、环和非法计划拦截 | 已实现 | 执行前校验，失败后有界修复 |
| TOOL / HUMAN 双轨验收 | 已实现 | 不可判定标准不能进入执行 |
| 验收标准绑定 DAG 节点 | 已实现 | 普通节点局部检查，最终集成全量检查 |
| Reviewer 声明与真实工具证据绑定 | 已实现 | 指定验证器未成功调用时不能通过 |

## 1. 为什么要做这个项目

**参考回答：**

我做 DevCLI 的原因，是开发任务和普通问答不一样。它需要读取真实仓库、修改多个文件、运行工具，而且中间任何一步都可能失败。单纯依赖模型连续对话，最大的问题不是模型不会写代码，而是缺少任务状态、依赖关系、权限边界、验收证据和失败恢复。

所以这个项目的核心不是增加几个 Agent，而是把模型的不确定输出放进确定性的执行框架：模型负责理解任务、拆解和提出候选实现；程序负责图校验、权限、调度、证据、提交和恢复。

**当前实现：** 已经具备 ReAct 与统一 Plan 两条公开执行路径，以及 DAG 调度、隔离工作区、Reviewer、checkpoint 和 PatchSet 提交。

**生产化还要补：** 从本地单用户 CLI 演进为多租户服务，增加身份认证、租户隔离、持久任务队列、分布式调度、统一审计、密钥托管、沙箱池和服务等级目标。

## 2. 整体架构和完整数据流是什么

**参考回答：**

默认入口是 ReAct，适合短任务；`/plan` 固定使用 Planner、Worker、Reviewer 协作。两条路径共享模型调用、工具执行、记忆、预算和运行事件；Plan 内部通过 DAG 校验和资源分波决定串行或并行，不再要求用户选择 Standard 或 Team。

Plan 的完整链路是：用户任务进入 Planner，Planner 生成步骤、依赖和验收标准；程序先校验 JSON、DAG 和验收标准；独立计划 Reviewer 在无工具上下文中检查原始需求是否映射到节点和验收标准，拒绝则退回 Planner 有界修订；机器评审通过后用户再确认；随后 Worker 隔离执行、Pre-Review 硬检查、产物 Reviewer 证据审查、PatchSet 冲突预检和主项目应用。步骤状态和恢复信息持续写入 checkpoint，未完成 checkpoint 恢复前重新评审计划。

**当前实现：** 这条本地闭环已经完成，执行结果、工具证据和 checkpoint 都有结构化对象承载。

**生产化还要补：** 把进程内调度改为持久化状态机。任务事件写入可靠存储，Worker 使用租约领取任务，所有状态迁移带版本号，服务重启或多实例竞争时仍能保证幂等。

## 3. 为什么需要 Plan，而不是一直使用 ReAct

**参考回答：**

我选择 Plan 不是因为 ReAct 架构有问题，也不是提示词写得不够好。两者解决的控制问题不同。ReAct 的决策单位是下一步动作，适合局部反馈闭环；Plan 的决策单位是完整任务图，能够表达跨模块依赖、并行边界、失败传播和恢复坐标。

提示词可以让模型先想一遍，但不能把自然语言承诺变成调度器能够检查的状态。记忆可以补充历史事实，但不能替代依赖图、节点终态和提交边界。因此短任务继续使用 ReAct，跨模块、可并行、需要恢复或严格验收的任务才使用 Plan。

**当前实现：** 模式由用户显式选择，执行完成后回到默认 ReAct，不根据任务文本自动切换。

**生产化还要补：** 可以增加只做建议、不静默切换的任务分类器。分类器输出复杂度、风险、预计成本和推荐模式，由用户或策略引擎确认后切换，并保留路由原因用于离线评估。

## 4. ReAct 失败后为什么选择 Plan，怎么兜底

**参考回答：**

一个典型失败是订单履约任务。单 Agent 能完成大部分模块，但容易漏掉退款后的授权清理、取消后的配送清理和幂等键冲突。这类失败不是某一步工具不会调用，而是跨模块不变量没有被持续维护。

Plan 的价值是先把库存、支付、配送、通知、审计和最终编排放进同一张依赖图，再由最终集成节点检查跨模块联动。受控实验中，单 Agent 通过 27 项隐藏检查，Team 通过 30 项，但耗时约为前者的 3.76 倍。这个结果只代表一次有效对照，不能直接推广为稳定收益。

**当前实现：** ReAct 失败不会自动转 Plan。系统会暴露失败或停滞，用户确认后重新以 Plan 发起，避免系统在后台改变成本、权限和提交语义。

**生产化还要补：** 定义可解释的升级条件，例如重复错误、跨三个以上模块、存在并行机会、需要补偿事务或超过单 Agent 预算。升级时冻结 ReAct 已产生的事实和副作用，生成迁移摘要，并要求用户确认新的预算和权限。

## 5. 任务图是模型直接生成的吗

**参考回答：**

DAG 的候选结构由 Planner 模型生成，但程序不直接信任。Planner 必须返回固定 JSON 协议，包括任务摘要、步骤、依赖和验收标准。模型输出前后可以有少量说明，程序只提取完整 JSON 对象。

解析后，程序会统一规范节点 ID，同时重写依赖和验收目标，然后检查重复节点、缺失依赖、环、阻塞性空工作区检查和不可执行验收标准。解析或结构校验失败时，会清空 Planner 的旧对话，携带明确失败原因重新生成，默认最多修复两次。

**当前实现：** 属于“模型生成候选图，确定性程序编译和拒绝”的混合方式，不是完全信任模型，也不是纯规则拆任务。

**生产化还要补：** 把计划协议做成版本化领域模型；增加最大节点数、最大图深、资源预算、风险等级和策略校验；常见任务可以先由模板生成骨架，再让模型补充，降低图结构漂移。

## 6. 一个节点最少包含哪些字段

**参考回答：**

当前节点最少包含四个字段：稳定 ID、可执行描述、任务类型和依赖 ID 列表。节点运行后还会形成统一执行产物，记录状态、输出摘要、修改资源、错误、尝试次数和时间戳。

验收标准不塞进节点正文，而是独立定义。当前执行前强制检查 ID、描述、通过信号、验证方式、验证器和适用节点；类别与严重程度可以额外携带。适用节点通过 `applies_to` 关联真实 DAG 节点，也可以使用 `FINAL` 表示最终集成义务。

**当前实现：** 节点字段足以完成本地调度和恢复，验收标准已经能够追踪到具体节点。

**生产化还要补：** 节点还应声明超时、最大尝试次数、幂等键、资源需求、预期产物、失败策略、补偿动作、数据敏感级别和负责人，避免调度器继续从自然语言猜测执行策略。

## 7. 依赖关系完全信任模型吗，环和不存在的依赖怎么处理

**参考回答：**

不信任。程序先建立节点 ID 集合，逐条检查依赖是否存在，再使用深度优先遍历检测环。任何缺失依赖或环都会在 Worker 启动前拒绝，不会边执行边猜。

对于可以修复的 Planner 输出，系统把具体错误反馈给 Planner 有界重生成；修复仍失败就终止计划。它不会擅自删除依赖，因为删除一条边可能改变业务语义。

**当前实现：** Plan 和 Team 使用同一套图校验与就绪判断，避免两条路径出现不同的 DAG 语义。

**生产化还要补：** 增加领域约束，例如数据库迁移必须先于应用发布、写路径变更必须先有兼容读；同时保存原始计划、修复前后差异和规则命中记录，便于审计 Planner 为什么改图。

## 8. DAG 执行时怎么并行，又怎么避免冲突

**参考回答：**

调度器只选择依赖已经满足的节点。同一批就绪节点先按修改资源拆成多个波次，没有冲突的节点才并行。Team 默认两个 Worker，并发还有硬上限。同一文件的写入通过资源租约限制为一个运行中节点持有，冲突时拒绝，不采用最后写入覆盖，也不让模型自动合并。

**当前实现：** 并行任务使用独立输出缓冲，结束后按稳定顺序归并；步骤结束会释放资源租约。

**生产化还要补：** 使用分布式租约和心跳，支持租约续期、Worker 失联回收、租户配额、优先级、背压和公平调度。资源声明应由 Planner 提供、程序静态分析和运行时访问记录共同校正。

## 9. 节点失败后是只重试该节点，还是级联回滚

**参考回答：**

当前策略是先局部恢复，不默认级联回滚。模型限流、超时和网络错误在 Provider 层指数退避重试；工具参数错误返回当前 Worker 修正；Reviewer 不通过时，原节点携带失败原因重新执行，最多两次；仍失败可以保持原 ID 和依赖原位换思路重做一次。额度耗尽后节点进入失败终态，普通后继不再执行。

这样设计是因为很多节点彼此独立，回滚已经通过的节点会扩大故障面，也会浪费模型调用和工具成本。

**当前实现：** Reviewer 重试次数目前是固定策略，Planner 修复轮数、Reviewer 内部轮数和模型网络重试可以配置。最终失败会输出已消耗额度、最后原因、checkpoint 和人工处理选项。

**生产化还要补：** 把重试策略下沉到节点协议，根据错误码决定是否重试，并配置次数、退避、超时和预算。所有可重试副作用必须有幂等键；连续失败进入熔断和人工队列，不能只靠统一次数。

## 10. 应不应该使用级联回滚

**参考回答：**

我不会把级联回滚设为默认策略。只有三个条件同时满足才考虑：上游结果已经产生外部可见副作用；下游失败破坏了整体业务不变量；系统存在经过验证的逆操作。

DevCLI 对本地文件采用隔离工作区和延迟提交。修改先留在隔离目录，审查通过后才形成 PatchSet 写回主项目，因此大部分失败根本不需要回滚主项目。写回前会检查原文件哈希；中途应用失败时根据备份恢复，并明确报告未恢复路径。

**当前实现：** 本地文件有提交级回滚，没有针对支付、消息和第三方 API 的通用级联补偿。

**生产化还要补：** 对外部副作用采用 Saga 补偿。每个节点声明正向动作、幂等键和补偿动作，补偿按照已完成副作用的逆序执行；补偿失败进入人工队列，并保留不可篡改的审计记录。

## 11. Review Agent 基于什么验收

**参考回答：**

Reviewer 不是只看 Worker 的一句总结。它能看到原始用户任务、当前节点、与该节点相关的验收标准、任务状态和结构化工具证据，并在同一个隔离工作区读取真实产物。代码步骤进入 Reviewer 前还要先经过编译类硬检查；硬检查失败会直接打回 Worker，不调用 Reviewer 模型。

Reviewer 输出必须是 JSON，包含是否通过、三项评分、逐条标准结果和问题列表。功能正确性必须满分，其他评分不能低于阈值。TOOL 标准如果声明使用某个验证器，本轮审查必须真实成功调用该验证器；模型在文本里声称“已经验证”不算证据。

**当前实现：** Reviewer 并不是直接消费一份预生成的完整代码 Diff，而是读取隔离工作区、任务上下文和工具证据。这能验证真实文件，但问题定位协议还不够细。

**生产化还要补：** 显式传入变更清单、结构化 Diff、基线版本、构建产物摘要和测试报告；Reviewer 的每个判断必须引用证据 ID，证据再映射到文件、命令、日志或测试结果，形成可追踪证据链。

## 12. 验收标准是谁定义的，Worker 能不能自己修改

**参考回答：**

候选验收标准由 Planner 根据原始任务生成，不由 Worker 自己总结。Worker 只能执行被分配的节点，不能降低标准。程序在执行前检查每条标准是否有明确通过信号、TOOL 或 HUMAN 验证方式、有效验证器和适用节点。

计划通过预检后先进入 Reviewer 语义评审，强制输出需求覆盖、节点引用、逐条验收标准结论和结构化问题；不通过会让 Planner 有界修订，协议损坏直接失败关闭。机器评审通过后，用户仍可执行、补充要求后重新规划或取消。

**当前实现：** 双轨验收、确定性预检、独立计划 Reviewer、人工确认和节点范围已经完成；旧 checkpoint 缺失验证方式时按人工验收处理，缺失节点范围时只放到最终集成阶段，恢复执行前重新进行计划语义评审。

**生产化还要补：** 高风险场景不能只让 Planner 定标准。应将组织级质量门禁、业务不变量、合规规则和用户标准合并，Planner 只能补充不能删除强制标准；标准变更需要版本和审批记录。

## 13. Review 不通过时返回什么

**参考回答：**

不是只返回一句“有问题”。当前返回结构化审查结果，包括总结、功能正确性、集成完整性、代码质量、每条验收标准是否通过、验证方式、证据和问题列表。编排器会把失败原因重新注入原 Worker，让它在同一个节点上修改。

**当前实现：** 已经能够把问题与验收项关联，但问题列表还没有强制包含文件、行号、期望值、实际值和证据 ID。

**生产化还要补：** 把问题改成稳定协议：问题编码、严重程度、验收项 ID、文件与行号、期望值、实际值、证据 ID、是否可自动修复。这样可以去重同一问题，也能判断 Worker 是否真的修复，而不是换一种表述。

## 14. Review 连续失败三次怎么办，如何避免死循环

**参考回答：**

系统用多层硬上限避免 Reviewer 和 Worker 无限拉扯。Reviewer 自己的模型循环有上限；节点审查不通过后最多重新执行两次；之后只允许一次保持原节点 ID 的原位重做，不创建新的平行计划。仍失败就保持 FAILED，保留 checkpoint，并输出人工升级信息。失败比例达到一半时，最终集成节点会熔断，不允许它把所有问题强行兜住。

**当前实现：** 达到上限后不会自动整图重规划，因为自动改图可能绕开原验收标准，也可能重复已产生的副作用。

**生产化还要补：** 增加失败指纹。如果相同验收项、相同证据和相同错误连续出现，就提前停止；只有错误类别发生变化或证据改善才继续。重新规划必须由独立策略触发，并继承原标准、已完成副作用和剩余预算。

## 15. 编译和工具都通过，但功能方向偏了，怎么发现

**参考回答：**

编译只能证明局部代码成立，所以当前设计有四道检查。执行前先做确定性预检，再由计划 Reviewer 检查原始需求到节点和标准的覆盖并交给用户确认；节点执行时，只检查与当前节点绑定的标准；最终集成时，再把原始任务和完整验收集合放回来，检查入口、默认参数和跨模块联动。

另外，自动验收只认可真实工具证据；无法稳定自动判断的视觉、产品取舍和主观质量必须标记为人工验收，不能让 Reviewer 伪装通过。受控评测还使用模型不可见的隐藏检查，防止 Worker 和 Reviewer共同接受同一个错误假设。

**当前实现：** 计划 Reviewer 能发现显式需求没有映射到节点或标准，但它与 Planner 仍可能共享同一理解偏差。总览审查官本质上仍是 Final integration 加完整标准回放，不是一个无所不知的新模型。

**生产化还要补：** 引入独立需求编译阶段，把原始意图拆成可追踪需求项；每个需求必须映射到验收标准、执行节点和证据。关键业务再增加契约测试、性质测试、历史回放、差分测试和人工签字，检测 Planner 与 Reviewer 的共同偏差。

## 16. 为什么每条标准必须声明验证方式

**参考回答：**

因为“实现得合理”“体验良好”这类标准没有可判定边界，执行结束后任何模型都可以主观解释。要求 Planner 同时回答“要什么”和“怎么证明”，才能在开工前发现不可执行标准。

TOOL 表示可以通过真实工具产生证据；HUMAN 表示必须由人检查。没有验证方式、通过信号、有效验证器或适用节点的标准都会被拒绝。人工标准不会进入自动通过结果，只会作为待确认义务保留。

**当前实现：** 双轨验证、执行前拦截、节点绑定和真实验证器调用检查均已完成。

**生产化还要补：** 建立验证器目录，记录版本、输入 Schema、可信级别、运行成本和适用环境；高风险标准要求两个独立证据源，避免单一测试或单一 Reviewer 成为共同故障点。

## 17. checkpoint 能恢复什么，不能恢复什么

**参考回答：**

当前 checkpoint 保存计划、依赖、验收标准、执行产物、步骤终态、Worker 绑定、消息游标、已消耗重做次数和 PatchSet 写前日志。恢复时优先重建原 DAG 和原 Worker 分配，不重新获得重试额度，也不恢复完整 Agent 私有对话。

如果写回过程中崩溃，系统根据目标文件最终哈希判断该步骤已经完成、仍待提交还是需要回滚。对账保存失败、回滚不完整或身份拓扑损坏时停止恢复。

**当前实现：** 协议版本是 v7，主要解决单机进程崩溃和本地文件提交恢复。

**生产化还要补：** checkpoint 需要进入事务型持久存储，并采用事件序列号和乐观锁；大产物放对象存储，只在状态库保存内容哈希和引用；跨服务恢复要结合幂等键、租约和补偿状态。

## 18. 多 Agent 为什么成功率更高，又为什么更慢

**参考回答：**

成功率提升不是因为 Agent 数量本身，而是因为职责和检查点发生了变化：Planner 先固定跨模块依赖，Worker 缩小单次上下文，Reviewer 独立检查，Final integration 再处理全局联动。它主要减少的是遗漏、模块之间的契约不一致和“模型说做了但实际没有执行”。

代价也很明确：多一次 Planner 调用、每个节点都可能触发 Reviewer、上下文被多次注入，失败时还有重试和重做。因此小任务使用 Team 反而不划算。

**当前实现：** 订单履约实验记录了隐藏检查完成率、耗时、调用次数和 Token。一次有效对照中，单 Agent 为 27/30，Team 为 30/30，Team 耗时约为 3.76 倍。

**生产化还要补：** 至少进行多模型、多任务、多次重复实验，报告成功率置信区间、端到端耗时、首 Token 延迟、P50/P95、Token、成本、工具次数、并行利用率和人工介入率；再通过消融实验分别测量 Planner、Reviewer、并行和最终集成的真实贡献。

## 19. 多 Agent 也救不回来的失败有哪些

**参考回答：**

第一类是 Planner 漏掉了用户意图，后面的 Worker 和 Reviewer都围绕错误标准工作；第二类是验证器本身覆盖不足，工具执行成功但没有检查关键语义；第三类是外部模型超时、限流或服务异常；第四类是外部副作用缺少幂等和补偿，重试可能放大影响；第五类是多个角色共享同一个错误前提，形成共同偏差。

项目早期还遇到过 Planner 输出非 JSON、把空工作区检查单独设为阻塞步骤、Worker 只描述准备修改却不调用工具、Reviewer 只写“已验证”等问题。现在前四种协议问题已经通过解析修复、计划预检、强制工具证据和真实验证器绑定处理，但原始意图遗漏仍然需要需求追踪、隐藏测试或人工评审。

**生产化还要补：** 建立失败分类和回放集，把每次失败沉淀为可重复评测；上线新模型、提示词或调度策略前必须跑回归，并采用小流量灰度和自动回退。

## 20. 如果现在要生产化，优先改什么

**参考回答：**

我会按风险而不是功能数量排序。

第一优先级是执行可信度：补齐结构化问题定位、需求到标准再到证据的追踪、节点级可配置重试和外部副作用幂等补偿。

第二优先级是运行可靠性：把 checkpoint 演进为持久任务状态机，增加分布式租约、Worker 心跳、超时回收、租户配额和人工介入队列。

第三优先级是安全与治理：统一身份认证、项目权限、秘密管理、网络出口策略、不可篡改审计和数据保留策略。

第四优先级才是性能：基于埋点决定哪些任务使用 ReAct、Plan 或 Team，再做并行度、自适应模型、缓存、上下文压缩和批量调用优化。

当前项目已经完成本地执行可信度的主要骨架，但还不能把“本地 Agent CLI”直接等同于“多租户生产平台”。面试时主动讲清这条边界，反而能体现工程判断。

## 面试收束版

如果面试官要求用一分钟总结，可以这样说：

> DevCLI 当前不是简单的多 Agent 对话，而是一套有确定性外壳的本地执行系统。模型生成计划和候选实现，程序负责 DAG 校验、节点级验收、真实工具证据、隔离工作区、PatchSet 提交、重试上限和 checkpoint 恢复。ReAct 与 Plan 是显式选择，因为两者的成本和执行语义不同。现在本地文件任务的可信执行链路已经闭合，但生产化还需要补持久调度、多租户安全、外部副作用幂等补偿、完整证据追踪和统计稳定的评测体系。
