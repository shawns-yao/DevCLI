# 上下文压缩设计

## 目标

在不破坏工具消息协议和关键约束的前提下，控制完整 LLM 请求的上下文规模。压缩对象不是旁路笔记，而是实际发送给模型的 `conversationHistory`。

## 请求预算

每次模型调用前，压缩阈值按以下预算计算：

```text
基础触发阈值 = min(模型上下文窗口 × 压缩比例, 模型上下文窗口 - 模型输出预留)
conversationHistory 有效触发阈值 = 基础触发阈值 - 当前工具定义 token
```

`ContextProfile.historyTriggerTokens(...)` 负责扣除额外请求内容，`TokenBudget.estimateToolDefinitionsTokens(...)` 负责估算当前工具定义。system prompt、当轮记忆、Skill 和 MCP 动态内容已经位于当前 history 或当轮消息中，不再单独创建第二份状态。

## 事实来源与恢复边界

- 生产压缩入口统一接收 `CompactionContext`，携带项目标识、会话标识、上下文 epoch、历史序号和来源事件范围。Runtime API 从持久事件时间线读取真实事件游标，并按稳定消息指纹关联 `model.context` / `model.message` 事件；`history:index` 仅作为没有运行时事件映射时的兼容回退。
- `CompactionFactExtractor` 将文件路径、命令、错误码、配置值、修改文件、符号、数字、决策和未解决事项绑定到会话、事件序号和 epoch。`sourceHash` 覆盖来源事件范围，避免跨轮次或跨会话错配事实。
- `CompactionSemanticGuard` 同时约束模型摘要和降级截断。事实补回后会再次执行事实一致性校验和最终 Token 预算检查；状态冲突只在同一事实子句或结构化摘要条目中判定，不使用全文关键词互相推断。
- 压缩边界持久化 `projectionHash`、来源事件范围、`snapshotRef` 和 `snapshotChecksum`。checkpoint/resume 会重新读取稳定引用并校验快照、事件范围和投影，校验失败时不恢复旧摘要。

## 原文尾部

`ConversationHistoryCompactor` 使用 token 预算从最新消息向前填充原文尾部，并在 `user` 边界切分，避免拆开 assistant tool call 与 tool result。

默认尾部预算为当前模型窗口的 8%，并夹在 4K～32K 之间；同时不超过当次 history 触发阈值的一半。切换模型后重新计算。显式传入的尾部 Token 预算保持原语义，供调用方和实验固定参数。

尾部原文预算、模型摘要预算和压缩后总 history 预算是三个独立概念。尾部预算只决定保留多少最近原文，不代表最终压缩结果的总大小；语义摘要必须单独记录其输入、输出和事实保真结果。

公开评测日志分别记录 `triggerTokens`、`tailBudgetTokens`、`summaryInputBudgetTokens`、`summaryTokens`、`retainedTailTokens` 和 `postCompactionHistoryTokens`。其中 Token 体积只解释压缩结构，效果结论仍以结构化关键事实保留率和压缩后 SWE-bench 官方结果为准。

如果边界对齐后仍然超出原文预算，只继续把最旧的保留轮次前移到摘要区；规则层不得截断 user、assistant、任务状态或决策文本。

## Microcompact

Microcompact 的职责是触发后的确定性工具结果淘汰，不是会话语义压缩，也不按新旧、尺寸或工具类型裁剪：

- 只在一次真实触发事件内执行，未配置输出根目录时整层跳过；只处理 `role=tool` 且带 `toolCallId` 的历史消息，不修改 user 或 assistant 消息，不删消息，保持 `tool_call` 配对。
- 判据只有两条，且都能由历史事实直接证明：`duplicate`（内容指纹与更早的工具结果相同）和 `isProvablyDead`（仅限 `read_file`，且同一 `path` 在更晚位置被 `write_file` / `edit_file` 写过）。内容指纹优先取结果元数据里的 `sha256=`，缺失时才回退正文哈希，避免恢复引用自身的差异被误判成重复。
- 不按工具类型、错误文本或“看起来重要”做语义判断，因此不设保留最近 N 项，也不设工具保护名单。记忆、外部查询和失败证据不由规则猜测，所以不参与淘汰。
- `DEVCLI_CONTEXT_MICROCOMPACT_KEEP_RECENT_TOOL_RESULTS` 与 `DEVCLI_CONTEXT_MICROCOMPACT_EXCLUDE_TOOLS` 已废弃，仅为编译兼容保留，不再驱动压缩决策。
- 折叠引用按结构识别，不按字符串包含：要求内容以 `<microcompact_boundary>` 起始、存在闭合标记且携带 `type=tool_result`。生成侧与消费侧共用 `MicrocompactBoundary` 的同一判定与常量，避免正文偶然提到该标记时被误判——消费侧误判会丢弃真实内容，生成侧误判只是跳过淘汰，方向相反。
- 空内容和已确认的折叠引用直接跳过，不重复处理。
- 被回收的完整结果写入项目 `.devcli/microcompact_tool_outputs/<session>/<toolCallId>.txt`，并写同名 `.sha256` 边车；`storedPath` 使用项目相对路径（正斜杠），可由隔离工作区中的 `read_file` 读取。
- 边界标记记录 `type`、`toolCallId`、`toolName`、`originalChars`、`reason`、`sourceToolCallId` 和 `storedPath`，`reason` 取 `duplicate` 或 `superseded`。
- 两条保护性放弃：折叠后 Token 不减少时原地保留；落盘失败时原地保留。短结果因此不会被换成更长的恢复引用，也不会留下没有节省收益的落盘文件。
- 语义摘要始终从本次压缩开始前的原始消息快照取证，不消费微压缩后的窗口投影，避免“先裁剪、再摘要”的二次损失。
- 淘汰不参与本次触发判定：触发与否只看压缩前的 Token，避免微压缩把越界状态悄悄清掉、导致语义压缩永不执行。
- 指标记录压缩前后总 Token、各角色 Token、按工具名称清理的 Token 和工具结果数量。
- 微压缩是触发事件内的前置步骤，不是二次触发条件：淘汰完成后继续执行模型语义压缩，是否摘要不重新以淘汰后的 Token 判定。

不采用 Anthropic 专属 `cache_edits`，避免破坏 Luna 和其他 OpenAI-compatible Provider 的统一链路。淘汰策略由 DevCLI 自身配置和公开数据实验决定，不复制逆向分析中的 5 个结果或 60 分钟规则，也不复制官方 API 的默认 3 个结果和 100K 阈值。

## 摘要策略

- 首次压缩：完整摘要请求能放入模型输入预算时只调用一次；确实超出时才 Map-Reduce。取消 60,000 字符分片上限，按完整提示词的 Token 估算动态分片，优先在消息文本边界切分，不切断 Unicode 代理对。
- 后续压缩：每批按“已有摘要 + 增量提示词 + 新增消息”的完整请求预算选择输入，提出 `ADD / UPDATE / RESOLVE / SUPERSEDE / EXPIRE / DELETE` 操作，程序校验后更新滚动摘要，再处理下一批；不先生成一堆独立摘要后无界拼接。
- 归并：按实际 Reduce 请求 Token 预算分组，最多八片不是窗口保证。不能归并、空分片或增量协议无效时，本次压缩失败，不以旧摘要冒充已吸收新增历史。
- 固定结构：新摘要保留六段；旧九段兼容读取但不携带任务状态投影。生命周期是每条事实的元数据，不新增或替换分段。
- 会话预摘要：生产端与正式压缩共用切分点，只覆盖可淘汰前缀；如果覆盖当前旧消息前缀且未过期，优先复用，当前切分范围扩大时使用前缀摘要继续增量更新。缓存指纹覆盖消息正文、推理、工具调用、来源和图片分片，并绑定 provider/model；确定性失败按输入指纹短暂冷却，不重复消耗模型调用。
- 周期性治理：默认每 5 次成功压缩执行一次生命周期 GC；清理过期事实和有界的覆盖审计，但不二次压缩稳定决策和未解决事项。
- 更新语义：同主题新值覆盖旧值，完成事项从活跃段迁移为最终结果；旧值退出有效 Prompt，仅保留有界审计。操作格式错误时保留原 history，不提交已处理的部分批次。
- 摘要提交前：执行 `CompactionSemanticGuard`，恢复缺失的命令、路径、版本、配置、禁止项和其他工作状态约束；降级截断也必须经过同一事实闸门。它不承担未来随机事实检索，也不能根据尚未出现的查询选择事实。
- 内容专用归约：代码摘要输入附带 diff 统计与指纹、符号、编译位置以及 RAG/index/classpath 版本；图片元数据附带来源、MIME、尺寸和基于图片字节的 SHA-256。OCR/视觉摘要属于可选 provider 能力，不以描述文本哈希替代图片身份。
- 超限重试：Provider 报告上下文超限时，将单次摘要输入预算乘以 0.75 后重新分片，最多重试三次；不再删除最旧 20% 轮次。学习到的预算仅作用于当前 compactor，切换模型时重置。原有连续失败熔断及带显式提示的紧急截断策略不在本次替换范围内。

## 摘要定稿顺序契约

摘要定稿固定为三段，顺序不可调换，逻辑集中在 `ConversationHistoryCompactor#finalizeSummary`：

```text
增长段：结构治理 → CompactionSemanticGuard 恢复受保护约束 → 事实修复
收敛段：capSummarySize（唯一一次）
校验段：事实一致性校验 + 尺寸上限 + 状态冲突（唯一一次提交判定）
```

**所有会「增长」摘要的步骤必须排在收敛之前；收敛只在全部增长完成后执行一次；末尾只做一次用于提交判定的校验。**

违反这个顺序的后果是静默的：前一步刚设好的上限被后一步撑破，而闸门在末尾必然拒绝，表现为「凡需要补回受保护约束的压缩永远无法提交」——不抛异常、不报错，只是压缩长期失败、上下文持续增长。

历史教训：早期版本在增长段之前先收敛一次，该收敛随即被语义守卫补回的约束撑破，导致尺寸闸门整轮拒绝。修正方式不是再补一层校验，而是把收敛移到全部增长之后并去掉重复收敛。

新增增长步骤时必须放在收敛之前；新增校验时优先复用末尾那一次，不要在中间插入。

## 触发时机

Agent 在每次模型迭代前执行轻量 token 检查。未超过完整请求预算时不调用摘要模型；超过后才执行 microcompact、摘要或降级截断。模型回答追加到 history 后，如果没有下一次迭代，压缩会延迟到下一次请求前执行，避免在不需要继续调用模型时额外发起摘要请求。

## 已知边界

- token 数是 DevCLI 统一估算器的结果，不等同于每个 Provider 的原生 tokenizer。
- 提示词和受保护的旧摘要本身已经超过预算时不能继续塞入新增消息；返回压缩失败，不暗中删除稳定事实。
- 生命周期 GC 只能治理已经进入结构化摘要的事实；此前已丢失且没有持久快照或事件引用的内容无法凭空恢复。
- 单条用户消息本身已经超过模型窗口时，Microcompact 不会删除它；该情况需要入口限制、附件化或显式语义处理，不能伪装成工具结果 GC。
- 完整请求预算仍依赖工具定义、Skill 和动态 MCP 内容在调用前可被当前 registry 正确枚举；外部 Provider 的隐藏 token 计费规则不在本地估算范围内。
- 高密度、未来查询未知且要求精确恢复的独立事实属于长期记忆检索问题，不适合用 bounded summary 证明。RULER NIAH 多键任务只能作为该边界的诊断或未来记忆检索评测，不能作为摘要质量的正式成绩。
